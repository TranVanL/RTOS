Phần 1 — Dựng OS-free control core và test host

Mục tiêu của phần này không phải làm motor chạy. Mục tiêu là thiết lập một đường đi đáng tin cậy: viết C lõi độc lập với OS → build trên máy host → chạy test tự động → sau này dùng lại đúng lõi đó trong FreeRTOS.

1. Bức tranh toàn cảnh: vì sao làm host trước?

M1 có hai môi trường chạy. Host dùng để chạy unit test và mô phỏng nhiều bước nhanh; QEMU/FreeRTOS dùng để kiểm tra task định kỳ, MPU, jitter và tích hợp. Nếu thuật toán bị gắn chặt vào RTOS ngay từ đầu, mỗi lần sửa PID lại phải build firmware và khởi động môi trường mô phỏng. Tách lõi ra cho phép kiểm tra phần toán học độc lập.

2. OS-free core là gì, và ranh giới nằm ở đâu?

“OS-free” không có nghĩa là không được dùng C standard library. Nó có nghĩa là phần lõi không phụ thuộc vào FreeRTOS, QNX, driver, mạng, UART hay cách chương trình được lập lịch. Dữ liệu cần để tính toán phải được truyền vào hoặc lưu trong đối tượng trạng thái của module.

Được phép trong core

  • C struct, enum, hàm và phép toán.
  • Trạng thái PID được truyền bằng con trỏ.
  • Tham số cấu hình và bước thời gian truyền rõ ràng.
  • Kiểm tra đầu vào nếu API quy định.

Không đặt trong core

  • xTaskCreate, vTaskDelayUntil hay queue FreeRTOS.
  • printf hoặc ghi UART trong mỗi lần tính.
  • malloc trong đường chạy điều khiển.
  • Đọc clock, sensor hoặc biến global ẩn.

Ví dụ luồng trách nhiệm trong một tick tương lai: adapter đợi tới tick → lấy snapshot measurement → gọi hàm core → áp dụng output → lưu telemetry. Core chỉ làm bước tính toán và không tự chờ hay tự log.

“Không printf trong core” không cấm test in lỗi. Nếu test cần thông báo lỗi, test runner có thể in. Quy tắc nhằm bảo vệ đường điều khiển trong firmware khỏi I/O không dự đoán được.

3. Trạng thái tường minh tạo tính tất định như thế nào?

PID có bộ tích phân và thường cần nhớ measurement/error của tick trước. Do đó hàm không chỉ là phép tính từ hai số; nó là một phép chuyển trạng thái. Với state tại tick k, tham chiếu và phép đo tại tick đó, core tạo output và state cho tick kế tiếp:

$$\big(x_k,\ r_k,\ y_k\big)\ \longrightarrow\ \big(u_k,\ x_{k+1}\big)$$

Trong đó x là state thuật toán, r là reference, y là measurement, u là output. “Tất định” nghĩa là nếu state ban đầu và toàn bộ chuỗi đầu vào giống nhau, kết quả chạy lại sẽ giống nhau trong cùng cấu hình chương trình.

Hàm PID sửa state qua con trỏ nên không phải “pure function” theo định nghĩa functional programming nghiêm ngặt. Tuy vậy, state được truyền tường minh, không có biến global, nên vẫn có thể replay và test đáng tin cậy. Điều cần tránh là state ẩn bên trong static/global khiến test này ảnh hưởng test khác.

Kiểm tra độc lập hai instance: tạo controller A và B, cho A chạy một chuỗi đầu vào; B chạy chuỗi khác. Kết quả của B không được phụ thuộc việc A đã chạy trước hay chưa.

4. Float: lựa chọn khởi đầu, không phải kết luận hiệu năng

Cortex-M3 không có FPU. Các phép toán float vì vậy thường được thực hiện bằng thư viện phần mềm. Ta chọn float trước vì dễ đọc và tuning; hiệu năng sẽ được đo ở Phần 7 thay vì suy luận từ cảm giác.

Nếu clock là 25 MHz và vòng điều khiển chạy 1 kHz, ngân sách lý tưởng trên mỗi tick là:

$$\frac{25\times10^6\ \mathrm{cycle/s}}{10^3\ \mathrm{tick/s}}=25\,000\ \mathrm{cycle/tick}$$

Ngưỡng đề xuất 30% là $7\,500$ cycle cho bước control cần đo. Đây là ngân sách kỹ thuật để điều tra, chưa phải yêu cầu hard real-time. Tổng chi phí còn gồm các phép toán khác, lời gọi hàm và phần chạy task.

5. API, tên kiểu C và hợp đồng đơn vị

Kế hoạch minh họa API khởi tạo controller và chạy một bước. Tách cấu hình bất biến khỏi state thay đổi thường giúp test dễ hơn: cấu hình chứa gain/giới hạn/dt; state chứa integral/giá trị lần trước. Chi tiết struct sẽ được quyết định khi đến phần PID, không cần viết cả thuật toán ở bài khung.

Tránh đặt type là pid_t trên Linux. POSIX dùng tên này cho process ID; tên dự án có thể xung đột với header hệ thống. Dùng tên đặc thù như control_pid_t hoặc pid_controller_t. Đây là điều chỉnh tên API để host build sạch, không thay đổi ý nghĩa PID.

Đơn vị là một phần của giao kèo API. Lõi M1 dùng rad, rad/s, V, A; encoder làm việc bằng count và cần chuyển đổi ở ranh giới phù hợp. Mỗi tham số cần được đặt tên/comment để người gọi biết đơn vị và không trộn degree với radian hoặc RPM với rad/s.

6. CMake, CTest và pytest: ba vai trò khác nhau

CMake cấu hình build

CMake mô tả source, include path, compiler options và test executable. M1 tạo cấu hình host riêng tại tests/control/CMakeLists.txt, vì repo hiện chưa có CMake gốc hợp nhất cho mọi subsystem. Như vậy host test không phụ thuộc toolchain ARM.

Compiler flags làm lỗi lộ ra sớm

  • -Wall -Wextra: yêu cầu GCC/Clang báo các cảnh báo phổ biến.
  • -Werror: biến cảnh báo thành lỗi build; build xanh có nghĩa không còn cảnh báo được bật.
  • -std=c11 / CMake C standard: cố định dialect C để host và firmware có hợp đồng rõ.

CTest chạy test đã đăng ký

Test executable cần được đăng ký bằng add_test(). CTest sau đó chạy chúng và trả pass/fail. Tên “CTest pass” chỉ xác nhận những test đã đăng ký thực sự chạy; vì vậy khi thêm test module mới, phải thêm nó vào cấu hình thay vì chỉ tạo file source.

pytest tích hợp vào luồng repo

Repo đang dùng python -m pytest tools -q. Một pytest wrapper có thể cấu hình build vào thư mục tạm, build test C, rồi gọi CTest. Nhờ vậy CI và người phát triển có một lệnh chung. Wrapper phải kiểm tra mã thoát và đưa stdout/stderr ra khi lỗi, nếu không build fail sẽ khó chẩn đoán.

Ba bước, ba loại lỗi: CMake configure lỗi thường là sai cấu hình/path; build lỗi thường là compiler/code; CTest lỗi là test chạy nhưng assertion hoặc chương trình thất bại. Tách bước giúp khoanh vùng nhanh.

7. Kiểm tra lõi không include FreeRTOS

Đây là architectural test: nó không kiểm tra PID đúng hay sai, mà bảo vệ ranh giới module. Test sẽ quét source/header trong common/control/ và báo lỗi nếu phát hiện include FreeRTOS như FreeRTOS.h, task.h, queue.h hoặc semphr.h.

Lúc thư mục chưa có source, kiểm tra có thể thông báo rằng chưa có file để quét. Khi thêm module, cùng test tự động bảo vệ file mới. Nếu quy tắc chỉ là grep thủ công, người phát triển có thể quên chạy; đặt nó trong CTest khiến nó thành một phần của cổng kiểm tra.

Giữ phạm vi quét đúng: chỉ quét core, không quét toàn repo. Adapter FreeRTOS được phép và cần include header RTOS; mục tiêu là đảm bảo phần OS-free không bị nhiễm phụ thuộc đó.

8. Bắt đầu thực hành — trình tự từng bước

  1. Xác nhận công cụ host: cần GCC, CMake và Python/pytest có sẵn.
  2. Tạo test smoke C: chỉ xác nhận compiler tạo được executable và chương trình chạy; ghi rõ đây chưa phải test thuật toán.
  3. Dựng CMake riêng: bật C11, -Wall -Wextra -Werror, đăng ký smoke test bằng CTest.
  4. Thêm architectural test: CTest gọi script kiểm tra header FreeRTOS trong core.
  5. Thêm pytest wrapper: pytest tự configure/build/ctest trong thư mục tạm để không làm bẩn source tree.
  6. Chạy riêng rồi chạy chung: chạy CMake/CTest trước để hiểu output, sau đó chạy pytest theo luồng repo.
  7. Chỉ khi nền xanh mới bắt đầu module: sau đây mới thêm plant/encoder/PID theo kế hoạch; không gộp lỗi hạ tầng build với lỗi thuật toán.

Các lệnh dự kiến từ thư mục gốc repo trên Linux:

cmake -S tests/control -B build/host-control
cmake --build build/host-control
ctest --test-dir build/host-control --output-on-failure
python3 -m pytest tools -q

Build host nằm trong build/host-control; pytest wrapper có thể dùng temporary directory và tự dọn sau test. Nếu thiếu compiler/CMake, cần xử lý môi trường trước thay vì bỏ qua test.

9. Checklist nghiệm thu và câu hỏi tự kiểm tra

  • Có CMake project host riêng ở tests/control/.
  • Build test C bằng -Wall -Wextra -Werror và tiêu chuẩn C cố định.
  • ctest --output-on-failure chạy ít nhất smoke test và architectural guard.
  • Core ở common/control/ không include FreeRTOS header.
  • pytest gọi được host test từ luồng python -m pytest tools -q.
  • Chưa tuyên bố hiệu năng Cortex-M3 dựa trên thời gian host.
  • API tránh tên pid_t để không xung đột POSIX.
