1M2 là gì & vì sao cần

Dự án là SIL (không có board thật): QNX supervisor ↔ FreeRTOS node trên QEMU, nối bằng UDP. UDP không có arbitration, không ACK, có thể mất/lặp/đảo/hỏng gói. Để mô phỏng một bus xe hơi đáng tin, ta cần:

Một định dạng frame chung

Giống CAN FD (ID 11-bit, DLC hợp lệ, tối đa 64 B), đóng gói trong 1 UDP datagram.

DBC làm nguồn sự thật

Một file mô tả signal; code C pack/unpack được sinh, không viết tay → hết lệch QNX vs FreeRTOS.

E2E protection

Phát hiện: hỏng bit (CRC), sai/nhầm message (Data ID), mất/lặp/đảo (counter), mất tín hiệu (timeout).

Công cụ quan sát

Python decoder + sniffer để nhìn thấy bytes trên dây và kiểm chứng độc lập với C.
Ranh giới M2 Có: codec, thư viện E2E, generator, sniffer, test. Không: Comm task hoàn chỉnh, FSM, E-stop end-to-end, timeout policy runtime — thuộc M3/M4. M2 chỉ cung cấp "viên gạch" và chứng minh viên gạch đúng.
Phạm vi trung thực (wording bắt buộc) Dùng "AUTOSAR E2E Profile 4–based", "CAN FD-compatible qua UDP", "in the spirit of ISO 26262". Không dùng "compliant". CRC không phải cơ chế bảo mật/xác thực. Không claim hard real-time hay xác thực phần cứng.

2Kiến trúc phân lớp

Vì sao tách lớp?

  • DBC chỉ là application payload → đổi E2E không phải sửa DBC, và công cụ DBC chuẩn (cantools) dùng được nguyên bản.
  • E2E không đếm padding: padding chỉ là thủ tục để khớp DLC hợp lệ, không mang thông tin → không vào CRC, length không tính nó.
  • Thư viện C thuần (không malloc, socket, FreeRTOS/QNX API, clock): chạy được trên QNX x86_64, Cortex-M3 và host test như nhau.

3DBC & sinh code (WP1)

DBC mô tả từng signal bằng: start|length@byte_order signedness (scale,offset) [min|max] "unit". Ví dụ:

BO_ 256 CMD: 7 QNX
 SG_ Mode      : 0|8@1+   (1,0) [0|3]  ""      FREERTOS
 SG_ VelLimit  : 8|16@1+  (1,0) [0|65535] "rpm" FREERTOS
 SG_ TargetPos : 24|32@1- (1,0) [-2147483648|2147483647] "count" FREERTOS

@1 = little-endian (Intel), + = unsigned, - = signed (two's complement). Do đó CMD = 1 + 2 + 4 = 7 B, TargetPos nằm ở byte 3–6.

tools/dbc_codegen.py làm gì

  1. Nạp DBC bằng cantools, kiểm inventory: đúng 5 message, đúng ID, độ dài, port UDP.
  2. Sinh common/generated/can_matrix.{c,h} (pack/unpack từng message, có range check) và can_matrix_meta.{c,h} (bảng ID, tên, payload length, port, timeout…).
  3. Chuẩn hoá output (loại timestamp, version header biến động) → chạy lại không sinh diff.
  4. --check: sinh vào bộ nhớ rồi so với file trên đĩa; lệch → exit ≠ 0. Dùng trong CI để bắt "sửa DBC mà quên regenerate" hoặc "ai sửa tay generated".
Nguyên tắcKhông bao giờ sửa tay common/generated/. Muốn đổi signal → sửa DBC → chạy generator → commit cả hai.

4E2E Profile 4–based

E2E trả lời: "Dữ liệu tôi nhận có đúng, đủ, mới, đúng thứ tự, đúng loại không?" bằng header 12 byte, little-endian:

length 0length 1 cnt 0cnt 1 id 0id 1id 2id 3 crc 0crc 1crc 2crc 3 payload…

length u16counter u16data_id u32 (= CAN ID zero-extend)CRC-32P4 u32app payload (DBC)

TrườngChống lỗi gì
lengthCắt/nối sai độ dài, nhầm kiểu message. Phải = đúng 12 + payload mong đợi.
counterMất frame, lặp (replay/duplicate), đảo thứ tự. Riêng cho từng Data ID.
data_idNhầm lẫn message (masquerade nhầm do routing). Phải khớp CAN ID của outer frame.
crc32Hỏng bit/byte ngẫu nhiên. Không chống tấn công cố ý.

API C (common/e2e/e2e.h)

bool e2e_protect(buf, cap, payload, len, counter, data_id, &out_len);   // Tx
void e2e_rx_reset(state, now);                                         // baseline + startup grace
e2e_status_t e2e_rx_verify(state, data, len, expected_payload_len,
                           expected_data_id, now, &payload_out);        // Rx
e2e_status_t e2e_rx_check_timeout(state, now, timeout_ticks);          // freshness
  • Không struct packed, không truy cập unaligned: đọc/ghi từng byte bằng read/write_u16/u32_le → độc lập endianness và alignment của CPU.
  • Không dùng clock nội bộ: caller truyền now (tick) → test chạy bằng "virtual tick", không sleep, tất định.
  • e2e_protect dùng memmove trước khi ghi header → payload được phép trùng với vùng đệm đầu ra.

Thứ tự kiểm tra trong e2e_rx_verify

Vì sao length/ID trước CRC?Không tính CRC trên buffer có độ dài không hợp lệ (tránh đọc quá buffer, và tránh CRC "đúng" cho message sai loại). Sau đó mới tính CRC rồi mới nhìn counter — vì counter của frame hỏng không đáng tin.

Golden vector ESTOP (đã kiểm độc lập)

Command=1, Reason=2, counter=0x1234, Data ID=0x10.

CRC input : 0E 00 | 34 12 | 10 00 00 00 | 01 02
CRC32P4   : 0x2A478334  → wire little-endian: 34 83 47 2A

Datagram dài 22 B = 6 + 16. Vector này nằm cố định ở tests/protocol/golden_vectors.md và được assert bởi cả C test, Python test và harness interop — không sinh từ bất kỳ implementation nào của dự án, nên chống được "C và Python cùng sai".

Giới hạn trung thựcĐây là vector của dự án, không phải vector conformance chính thức của AUTOSAR. Chỉ "123456789" → 0x1697D06A là known-answer chuẩn của tham số CRC.

Quy tắc vàng: lỗi không được mutate state Nếu một frame hỏng/lặp được phép làm mới "last accepted", kẻ gây lỗi có thể giữ cho timeout không bao giờ nổ trong khi dữ liệu thật đã mất. Test test_repeated_wrong_sequence_and_crc_error_do_not_advance_state khoá hành vi này.

Timeout wrap-safe

elapsed = now - reference;            // uint32 unsigned: luôn đúng modulo 2^32
reference = has_last_counter ? last_accepted_at : started_at;   // startup grace
timeout  = (elapsed >= timeout_ticks);
// ví dụ wrap: ref=0xFFFFFFF0, now=5  → elapsed = 21 (không phải số âm khổng lồ)
  • Startup grace: trước frame đầu tiên, so với started_at (thời điểm e2e_rx_reset) — không báo timeout ngay lúc vừa khởi động.
  • timeout_ticks < 2³¹ để phép so sánh còn nghĩa khi đồng hồ wrap.
  • Timeout không reset counter. Sau timeout, frame kế vẫn phải qua kiểm tra sequence; muốn chấp nhận lại baseline phải gọi e2e_rx_reset() tường minh (chính sách resync thuộc M4).

E-stop gửi 3 lần

Mỗi bản sao có counter tăng riêng (không replay nguyên datagram) → receiver đánh giá bình thường (delta 1). Hành vi "dừng" ở tầng ứng dụng phải idempotent.

7Outer frame & validate (WP3)

OffsetFieldSizeQuy tắc
0magic20xCAFD LE → bytes FD CA
2can_id2LE; 11-bit (5 bit cao = 0); phải thuộc DBC
4flags1bit0 FDF = 1 (bắt buộc), bit1 BRS = 0 trong M2, bit2–7 = 0
5dlc1số byte data (không phải code 4-bit); ∈ {0–8,12,16,20,24,32,48,64}
6datadlc[E2E][padding 0x00]

can_frame_decode từ chối (mỗi lỗi một status riêng): datagram ngắn/thừa byte (6 + dlc phải khớp chính xác), sai magic, ID ngoài miền hoặc không có trong DBC, flags sai, DLC không hợp lệ, E2E length > DLC hoặc ≠ độ dài mong đợi, padding khác 0, thiếu capacity. Không ghi vượt buffer khi input ngắn.

Vì sao từ chối padding ≠ 0?Padding không nằm trong CRC, nên nếu cho phép byte tuỳ ý, đó là kênh "dữ liệu ẩn" không được bảo vệ. Ép = 0 loại bỏ khả năng đó.
Vì sao UDP port lại thuộc protocol?Một socket riêng cho E-stop (5001) cho phép thread/task ưu tiên cao nhất xử lý nó độc lập — UDP không có priority, nên ưu tiên được hiện thực ở tầng ứng dụng.

Ý nghĩaLogic giao thức đã được chứng minh trên host, bằng hai implementation độc lập (C, Python) + một vector cố định. Phần còn thiếu là bằng chứng môi trường (compiler mục tiêu, CI sạch) — không phải lỗi logic đã biết.

Cái M2 KHÔNG chứng minh

  • Không phải "AUTOSAR-compliant", không có vector chính thức; không phải ISO 26262 compliant.
  • Không mô phỏng arbitration/ACK/bus-off CAN thật, không có timing phần cứng.
  • Chưa có đường chạy thật: freertos/app/net.c vẫn là echo/probe; Comm task, FSM, timeout policy, E-stop end-to-end → M3/M4.
  • "Đúng với bộ vector/test đã định nghĩa", không phải "đúng tuyệt đối".

12Bài học & bẫy

1. Round-trip cùng một implementation không chứng minh gì Encode rồi decode bằng cùng code vẫn pass dù thuật toán sai. Phải có (a) known-answer chuẩn, (b) vector tạo độc lập, (c) implementation thứ hai bằng ngôn ngữ khác.
2. DLC là byte-length, không phải mã 4-bit CAN FD thật mã hoá 12/16/20/24/32/48/64 B thành mã 9–15. Wire format của dự án lưu số byte trực tiếp để đơn giản; ARCH cũ nói nhập nhằng nên đã sửa ở WP0.
3. length không gồm padding; CRC không gồm CRC field & padding Nhầm hai điểm này là lỗi interop kinh điển (C tính padding, Python thì không). Test độ dài/padding cho cả 5 message bắt chúng.
4. Frame lỗi không được làm mới freshness Nếu không, timeout bị "nuôi" bằng rác. Đã khoá bằng test.
5. WRONG_SEQ không tự resync Receiver giữ last_counter cũ → nếu sender reset, mọi frame tiếp theo có thể bị WRONG_SEQ cho tới khi gọi e2e_rx_reset(). Đây là chủ ý (an toàn), nhưng M4 phải định nghĩa khi nào supervisor/node được phép reset.
6. Wrap của counter và tick Luôn dùng phép trừ unsigned cùng kích thước; không so sánh now > deadline.
7. "Tests pass" khác "xong" Plan tự đặt cổng: chưa có CI xanh + log cross-build thì không được ghi M2 Done. Thói quen này tránh khai khống trong CV/README.
8. Lỗi CI YAML do indent Từng làm workflow không hợp lệ; luôn parse YAML trước khi push (đã sửa; vẫn cần remote run để xác nhận).

13Việc cần làm để chốt M2

  1. Cài ARM toolchain (sudo apt install gcc-arm-none-eabi hoặc bản Arm GNU Toolchain), rồi: 
    cd freertos
cmake --preset <node-preset>        # xem CMakePresets.json
cmake --build --preset <node-preset> 2>&1 | tee ../docs/results/m2_arm_build.txt
arm-none-eabi-gcc --version | tee -a ../docs/results/m2_arm_build.txt
    Mục tiêu: firmware build sạch với can_frame.c, e2e.c, crc32p4.c, can_matrix*.c.
  2. Lưu log host vào docs/results/ (versions + lệnh + kết quả: gen-check, pytest, ctest).
  3. Review golden vector lần cuối; (tuỳ chọn) đối chiếu tham số CRC-32P4 với tài liệu AUTOSAR công khai và ghi nguồn — nếu không làm thì giữ nguyên "Profile 4–based".
  4. Commit + push toàn bộ M2, chờ GitHub Actions xanh. Nếu đỏ vì cantools khác version → pin version trong tools/requirements.txt rồi regenerate.
  5. Sau khi xanh: đổi traceability REQ-COM-001/002/003, REQ-SAF-004/005 sang Done; cập nhật README.md, docs/02_PROJECT_PLAN.md, CLAUDE.md ("M2 complete"); tick các ô §6 trong m2_plan.md.
Nếu không cài được ARM GCC trên máy nàyCó thể để CI cài toolchain (apt-get install gcc-arm-none-eabi trong một job riêng) — khi đó log CI chính là evidence cross-build; plan cho phép "CI hoặc local theo môi trường đã chốt".

14Tự kiểm tra (để hiểu sâu)

Q1. Vì sao CMD có DBC payload 7 B nhưng wire data là 20 B?7 + 12 (E2E header) = 19 = E2E length; DLC hợp lệ nhỏ nhất ≥ 19 là 20 → 1 byte padding 0x00. Datagram = 6 + 20 = 26 B.
Q2. last_counter = 65534, nhận counter = 1 → status?delta = (uint16)(1 − 65534) = 3 → WRONG_SEQ (mất 2 frame: 65535 và 0).
Q3. Frame có CRC sai nhưng counter hợp lệ. Counter lưu có đổi không?Không. CRC_ERR được trả trước khi xét counter, và mọi status ≠ OK không mutate state.
Q4. Vì sao padding không vào CRC mà vẫn phải bằng 0?CRC không bảo vệ nó; nếu cho tuỳ ý thì thành kênh dữ liệu không được bảo vệ. Decoder từ chối ≠ 0.
Q5. started_at = 1000, chưa có frame nào, now = 1060, timeout 50 → ?elapsed = 60 ≥ 50 → TIMEOUT (tham chiếu là started_at do chưa có frame OK).
Q6. Vì sao cần implementation Python riêng thay vì chỉ test C?Để phát hiện lỗi đối xứng (cùng hiểu sai spec) và lỗi hiểu nhầm byte-order/length mà round-trip C↔C không thấy.
Q7. Vì sao gửi E-stop 3 lần lại không phải 3 datagram y hệt?Datagram y hệt → 2 bản sau bị REPEATED (không phải frame mới). Dùng counter tăng → mỗi bản là frame hợp lệ; ứng dụng xử lý idempotent.
Q8. Mất đúng 2 frame liên tiếp thì chuyện gì xảy ra? Mất 1 frame?Mất 1 → delta 2 → OK. Mất 2 → delta 3 → WRONG_SEQ.
