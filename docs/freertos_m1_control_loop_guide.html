1. M1 làm gì — và chưa làm gì?

M1 xây dựng một motion node điều khiển mô phỏng chạy trên FreeRTOS. Công việc được chia lớp để thuật toán điều khiển có thể kiểm thử trên máy host mà không cần kernel, QEMU hay mạng.

2. Sơ đồ tín hiệu: controller đang điều khiển cái gì?

Quy ước tín hiệu đề xuất: θ_ref là vị trí đích (rad), θ_meas là encoder position (rad), ω_ref là tốc độ tham chiếu (rad/s), ω_meas là tốc độ đo/ước lượng (rad/s), u là điện áp motor (V), i là dòng (A). Plant lưu trạng thái thật; controller chỉ nhìn feedback cảm biến, không được đọc trực tiếp state thật — nếu không mô phỏng như có cảm biến hoàn hảo và encoder model mất ý nghĩa.

Đơn vị là hợp đồng: ghi đơn vị vào tên hoặc comment của mọi tham số. Đừng trộn vòng/phút với rad/s, độ với rad, encoder count với góc, hay normalized command với volt.

3. Mô hình motor DC — suy ra phương trình thay vì học thuộc

3.1 Mô hình điện phần ứng

Điện áp đặt lên cuộn dây dùng để thắng điện trở, tạo biến thiên dòng qua điện cảm, và bù sức điện động phản kháng (back-EMF). Với quy ước chiều dương nhất quán:

$$L\frac{di}{dt}=u-Ri-K_e\omega$$

u [V] là điện áp actuator; i [A] là dòng; R [Ω] là điện trở; L [H] là điện cảm; K_e [V·s/rad] là hằng số back-EMF; ω [rad/s] là tốc độ trục. Motor quay nhanh hơn thì back-EMF lớn hơn, làm dòng giảm — feedback vật lý tự nhiên của motor.

3.2 Mô hình cơ học

Mô-men điện từ kéo rotor; quán tính chống thay đổi tốc độ; ma sát nhớt tỷ lệ với tốc độ; tải ngoài có thể cản hoặc kéo trục:

$$J\frac{d\omega}{dt}=K_t i-b\omega-\tau_{load}$$

J [kg·m²] là quán tính; K_t [N·m/A] là hằng số mô-men; b [N·m·s/rad] là hệ số ma sát nhớt; τ_load [N·m] là mô-men tải. Nếu project chưa mô hình tải, đặt bằng 0 nhưng vẫn nên giữ input để sau này test disturbance.

3.3 Động học vị trí

$$\frac{d\theta}{dt}=\omega$$

θ [rad] là góc. Một điểm dễ nhầm: động học điện-cơ từ điện áp tới tốc độ là bậc hai (trạng thái i, ω); nếu thêm vị trí θ, mô hình state-space có ba trạng thái vì vị trí là tích phân của tốc độ. Trong giao tiếp kỹ thuật, có thể gọi “motor DC bậc hai” khi nói transfer function điện áp→tốc độ, nhưng code mô phỏng position cần giữ cả θ.

3.4 Dạng trạng thái dùng trong code

Đặt trạng thái x=[i, ω, θ]; đạo hàm theo thời gian là:

$$\dot{x}=f(x,u,\tau_{load})=\begin{bmatrix}(u-Ri-K_e\omega)/L\\(K_ti-b\omega-\tau_{load})/J\\\omega\end{bmatrix}$$

Plant API nên nhận input tại một bước, cập nhật trạng thái nội bộ và trả snapshot. Giao diện C thuần có thể khái niệm như sau (không phải code final):

typedef struct {
    float resistance_ohm, inductance_h, inertia_kg_m2;
    float viscous_friction, torque_constant, back_emf_constant;
    float load_torque_nm;
    float sample_period_s;
} PlantConfig;

typedef struct {
    float current_a, velocity_rad_s, position_rad;
} PlantState;

void plant_reset(PlantState *state, const PlantConfig *cfg);
void plant_step(PlantState *state, const PlantConfig *cfg, float voltage_v);

Giữ PlantConfig (tham số bất biến) tách khỏi PlantState (i, ω, θ thay đổi) để test cùng một config với nhiều trạng thái/trace. Hàm phải xử lý cấu hình không hợp lệ (R/L/J ≤ 0), NaN/Inf nếu dùng float, và trạng thái ban đầu.

4. Tích phân số: Euler và RK2

Phương trình vi phân nói hệ thay đổi liên tục, nhưng task chạy từng bước dt=1 ms. Numerical integrator xấp xỉ thay đổi trong mỗi bước. Ta giả định điện áp u giữ cố định trong chu kỳ (zero-order hold), cập nhật plant một lần mỗi tick điều khiển.

4.1 Forward Euler

$$x_{k+1}=x_k+\Delta t\,f(x_k,u_k)$$

Ưu điểm: ngắn, rẻ, dễ debug. Nhược điểm: sai số cục bộ bậc hai theo dt, có thể mất ổn định nếu bước quá lớn so với dynamics nhanh. Một sanity check cho phần điện riêng (bỏ back-EMF, phương trình di/dt=−(R/L)i) là cần dt < 2L/R để Euler không phân kỳ; để có độ chính xác tốt thường cần dt nhỏ hơn nhiều so với hằng số thời gian điện τ_e=L/R. Điều kiện này chỉ là check sơ bộ, không phải chứng minh ổn định toàn hệ đóng vòng.

4.2 RK2 midpoint

$$k_1=f(x_k,u_k),\qquad k_2=f\left(x_k+\frac{\Delta t}{2}k_1,u_k\right),\qquad x_{k+1}=x_k+\Delta t\,k_2$$

RK2 đánh giá đạo hàm ở đầu bước rồi ở midpoint; sai số cục bộ bậc ba, toàn cục bậc hai trong điều kiện thông thường. Thường chính xác hơn Euler với cùng dt nhưng tốn thêm phép tính. Dùng cùng input trong cả hai lần đánh giá của RK2, vì actuator input được giữ nguyên trong chu kỳ đó.

4.3 Chọn tích phân theo bằng chứng

  • Chọn chu kỳ lấy mẫu dt từ task timing, không hard-code khác với 1 ms FreeRTOS tick.
  • So sánh Euler và RK2 với cùng bộ tham số, cùng input và cùng initial state; kiểm tra xu hướng và hội tụ khi giảm bước (ví dụ dt/2 trong host simulation).
  • Không nên ép thời gian mô phỏng lên host wall-clock. Host test có thể chạy một triệu bước nhanh hơn thực; thời gian mô phỏng là k·dt.
  • Ở bước đầu, chọn parameter set có đơn vị nhất quán và dynamics đủ chậm so với dt. Ghi rõ đây là tham số SIL minh họa, không phải đặc tính motor thật.
Không “sửa” lỗi tích phân bằng PID: nếu plant bùng nổ khi input hằng, trước tiên kiểm dấu, đơn vị, dt, overflow và stability của numerical method. Controller không nên che bug của plant.

5. Encoder: quantization, noise và stuck fault

5.1 Lượng tử hóa

Với N counts/revolution (CPR theo đúng định nghĩa project), số đếm lý tưởng từ góc là:

$$c_{ideal}=\theta\frac{N}{2\pi},\qquad c=\operatorname{round}(c_{ideal}),\qquad \theta_{meas}=c\frac{2\pi}{N}$$

Độ phân giải góc một count là 2π/N; sai số lượng tử hóa lý tưởng không nhiễu tối đa xấp xỉ nửa count: π/N rad. Xác định rõ N là count/vòng sau giải mã quadrature hay số vạch vật lý; nếu định nghĩa khác nhau sẽ sai hệ số ×2/×4.

5.2 Nhiễu Gaussian và khả năng tái lập

Mô hình hóa nhiễu góc hoặc nhiễu count với phân phối chuẩn trung bình 0, độ lệch chuẩn σ. Dùng PRNG có seed đưa từ test/config để cùng seed → cùng chuỗi mẫu; không dùng random seed theo thời gian nếu unit test cần reproducible. Box–Muller là một cách tạo mẫu chuẩn từ hai uniform:

$$z=\sqrt{-2\ln U_1}\cos(2\pi U_2),\quad U_1\in(0,1],\ U_2\in[0,1),\quad n=\sigma z$$

Nhiễu Gaussian không bị chặn tuyệt đối; test theo thống kê hoặc giới hạn an toàn của mô hình, không khẳng định mọi mẫu nằm trong ±3σ. Có thể bắt đầu không nhiễu, rồi thêm noise trong test riêng. Cortex-M3 không có FPU phần cứng; sqrt/log/cos có thể đắt nếu sinh nhiễu mỗi tick. Mô hình này không bắt buộc nằm trong đường control 1 kHz ngay từ đầu — có thể sinh noise trong test/offline hoặc dùng PRNG và bảng xấp xỉ sau khi đo chi phí.

5.3 Encoder stuck là lỗi cảm biến, không phải lỗi plant

Khi bật cờ stuck, encoder output giữ nguyên count đã chốt dù plant vẫn quay. Không đóng băng plant state: như vậy test sẽ không mô phỏng được mismatch giữa chuyển động motor và phản hồi encoder. Định nghĩa rõ semantics: kích hoạt stuck thì chốt current reading; clear fault thì tiếp tục từ reading thật hay cần reset — chọn một quy tắc và test nó.

Encoder model chỉ tạo điều kiện cho F8; việc phát hiện stuck cần observer/safety logic: ví dụ command/actuator cho thấy có chuyển động dự kiến, nhưng encoder delta vẫn 0 quá thời gian/ngưỡng. Threshold phải tránh báo lỗi khi setpoint đứng yên, tốc độ rất thấp, hoặc lượng tử hóa chưa đủ tạo count mới. Phát hiện lỗi và đưa FSM sang SAFE_STOP là phần safety behavior; model chỉ tạo stimulus đáng tin.

6. Cascade PID — hai vòng, hai tốc độ/tầng vật lý

6.1 Vì sao dùng cascade?

Vòng ngoài điều khiển vị trí, nhưng motor nhận điện áp/mô-men chứ không nhận trực tiếp vị trí. Vì vậy vòng vị trí tạo ra tốc độ mong muốn; vòng tốc độ điều khiển motor để bám tốc độ đó. Vòng tốc độ thường phản ứng nhanh hơn vòng vị trí. Trong M1 cả hai có thể chạy cùng một task 1 kHz để đơn giản và tất định; “cascade” mô tả quan hệ tín hiệu, không bắt buộc hai task/chu kỳ riêng.

ω* − ωmeasSai số tốc độ [rad/s]
PID tốc độTạo u* [V]
Motor + limitsu_applied → plant

6.2 PID rời rạc

Dạng song song liên tục là u=Kp·e + Ki∫e dt + Kd·de/dt. Trong code rời rạc tại chu kỳ Ts, tích phân cộng e·Ts, đạo hàm lấy sai phân (e[k]−e[k−1])/Ts. Đơn vị gain phụ thuộc input/output của từng vòng; gain vị trí không thể dùng lại gain tốc độ.

$$I[k]=I[k-1]+K_iT_s e[k],\qquad D[k]=K_d\frac{e[k]-e[k-1]}{T_s},\qquad u_{raw}[k]=K_pe[k]+I[k]+D[k]$$

Trong triển khai thật, chọn một biểu diễn nhất quán: lưu integral state đã nhân Ki (đơn vị output) hay lưu tích phân lỗi chưa nhân Ki. Cả hai được, nhưng anti-windup, reset và giới hạn phải theo đúng biểu diễn đó. Tách state của PID (integral, previous measurement/error, filtered derivative, previous output) khỏi tham số cấu hình giúp test nhiều input sequence với nhiều state độc lập.

6.3 Outer position loop

Outer loop nhận eθ=θref−θmeas và tạo ωref. Một khởi đầu phổ biến là P hoặc PI (D ở vị trí thường không cần thiết nếu inner speed loop đã dập dynamics; nhưng dự án yêu cầu cascade PID nên cần xác định PID ở cả hai tầng hay PID dạng tổng thể rồi giải thích thiết kế). Clamp tốc độ tham chiếu:

$$\omega_{ref}=\operatorname{sat}(u_{pos,raw},-\omega_{max},+\omega_{max})$$

Từ “PID cascade” thường được hiểu có controller position và controller speed; không nhất thiết cả hai phải dùng đủ P/I/D. Thiết kế cần ghi rõ loại từng vòng và lý do. Derivative trên measurement thường tránh “derivative kick” khi setpoint nhảy bậc; filter derivative giảm khuếch đại nhiễu encoder.

6.4 Inner speed loop

Inner loop nhận eω=ωref−ωmeas rồi tính điện áp motor. Đây là output điều khiển plant. Nếu mô hình output là voltage, saturation hợp lý là [−Vmax,+Vmax]. Nếu output được chuẩn hóa, ghi rõ map normalized command sang voltage và saturation ở đâu.

6.5 Anti-windup — ngăn integral “tích nợ”

Khi actuator chạm giới hạn, output thực tế không còn bằng output PID yêu cầu. Nếu vẫn cộng lỗi vào integral, integral tiếp tục lớn trong lúc motor không thể tạo thêm lực; khi lỗi đổi dấu, controller mất lâu mới thoát bão hòa (windup), gây overshoot/settling xấu.

Conditional integration / clamping: không tích phân khi output đã bão hòa và sai số sẽ đẩy output sâu hơn vào cùng phía saturation; vẫn cho tích phân nếu sai số giúp controller thoát saturation. Dễ triển khai nhưng logic biên cần test.

Back-calculation: phản hồi chênh lệch giữa output bị giới hạn và output thô về integral state:

$$I[k+1]=I[k]+K_iT_s e[k]+K_{aw}T_s\big(u_{applied}[k]-u_{raw}[k]\big)$$

Kaw là gain tracking (đơn vị phụ thuộc cách lưu integral). Dấu phải đúng: nếu raw vượt +Vmax thì u_applied−u_raw<0, kéo integral xuống. Anti-windup nên dùng output cuối cùng thật sự áp dụng, kể cả sau slew-rate limit, không chỉ amplitude clamp trước đó.

6.6 Tuning theo thứ tự

  1. Kiểm tra sign: tăng điện áp dương phải làm ω, sau đó θ tăng theo quy ước.
  2. Tắt outer loop; tune speed loop trên speed target đơn giản. Tăng Kp tới bám đủ nhanh nhưng chưa rung, thêm Ki để xóa steady-state error do tải/ma sát; quan sát saturation.
  3. Bật position loop, bắt đầu với P nhỏ để tạo tốc độ reference; tăng từ từ, áp giới hạn tốc độ, rồi mới thêm integral nếu có lý do.
  4. Chỉ thêm derivative khi cần damping và measurement đủ sạch; lọc D, tránh derivative kick.
  5. Chạy step cả hai hướng, nhiều biên độ; test saturation lâu rồi đảo setpoint để bắt windup.
Không tune bằng cách “thử số ngẫu nhiên”: ghi gain, plant parameters, Ts, limits, initial state và kết quả mỗi run. Một thay đổi mỗi lần giúp biết nguyên nhân overshoot hoặc dao động.

7. Saturation, rate limit và giới hạn vị trí

7.1 Ba giới hạn khác nhau

Giới hạnÝ nghĩaVí dụ áp dụng
Amplitude saturationActuator không thể vượt biên độ vật lýĐiện áp u∈[−Vmax,+Vmax], speed ωref∈[−ωmax,+ωmax]
Rate / slew limitActuator/reference không thể đổi nhanh tùy ý|u[k]−u[k−1]|≤Smax·Ts

Rate limiter rời rạc có thể lấy target difference rồi clamp vào [−Smax·Ts,+Smax·Ts], sau đó cộng lại output trước. Phải định nghĩa giới hạn áp ở ω reference, voltage, hay cả hai; không đặt cùng tên “rate limit” cho các tầng không phân biệt.

7.2 Soft limits không chỉ là clamp setpoint

Clamp target ngoài [θmin,θmax] ngăn target phi lý nhưng chưa chắc dừng được motor đang tiến nhanh về biên vì inertia. Khi gần biên, giới hạn tốc độ hướng ra ngoài theo khoảng cách còn lại, hoặc giảm command để phanh. Tối thiểu, tại biên không được tiếp tục cấp lực hướng ra ngoài; hành vi khi target vượt biên cần nhất quán: reject, clamp, hay SAFE_STOP — hợp đồng này nên đồng bộ với QNX ở milestone tích hợp.

Soft limit là lớp điều khiển; hard safety limit/SAFE_STOP là lớp bảo vệ khác. SIL plant không thay thế công tắc hành trình vật lý.

8. Step response và acceptance có thể kiểm chứng

Step test: giữ target ban đầu ổn định; tại thời điểm mô phỏng t0 đổi target từ θ0 sang θf; ghi target, θ thật, θ đo, ω, u và thời gian mô phỏng mỗi sample. Đừng đánh giá overshoot chỉ từ log thưa hoặc từ host wall-clock.

8.1 Overshoot

Với bước dương có biên độ A=θf−θ0>0, overshoot phần trăm:

$$s=\operatorname{sign}(\theta_f-\theta_0),\qquad M_p=100\%\cdot\frac{\max\left(0,\max_t\left[s(\theta(t)-\theta_0)\right]-|\theta_f-\theta_0|\right)}{|\theta_f-\theta_0|}$$

Công thức dùng cùng một hướng chuẩn hóa cho bước dương và âm; khi biên độ bước bằng 0 thì metric không xác định và test phải bỏ qua. Yêu cầu M1 là Mp<10%. Ghi rõ tính trên vị trí thật của plant hay vị trí encoder; nên xuất cả hai, nhưng acceptance controller thường dùng feedback/plant output đã định nghĩa thống nhất.

8.2 Settling time và steady-state error

Settling time cần định nghĩa tolerance band, thường biểu diễn tương đối theo biên độ step, và thời gian phải nằm ổn định trong band liên tục (không chỉ lần đầu đi qua). Project plan để “theo thông số chọn”, vậy trước khi kết luận pass phải chốt bằng văn bản/test config: ví dụ tolerance 2% hay 5%, yêu cầu ở trong band liên tiếp bao nhiêu ms, thời lượng test tối đa. Không được thay tiêu chí sau khi xem kết quả để biến fail thành pass.

Steady-state error là θref−θ sau khi quá độ kết thúc; PID integral thường giảm sai số này nhưng có thể gây windup nếu actuator bị giới hạn.

9. Control task 1 kHz trong FreeRTOS

9.1 Tick và chu kỳ

Project hiện đặt configTICK_RATE_HZ=1000 trong [FreeRTOSConfig.h](../freertos/app/FreeRTOSConfig.h), nên 1 tick danh nghĩa là 1 ms virtual time của firmware. configCPU_CLOCK_HZ=25 MHz dùng để cấu hình port/tick; trong QEMU/SIL, thời gian virtual và thời gian host wall-clock không nhất thiết bằng nhau.

Dùng vTaskDelayUntil(&xLastWakeTime, period) để giữ pha định kỳ: mỗi deadline dựa trên mốc trước đó, không cộng “thời gian chạy + delay” như vTaskDelay. Nếu task chạy lâu, không thể bù bằng việc giả vờ chưa trễ: phải detect/ghi overrun và xác định safe behavior.

initialize xLastWakeTime once
loop:
    wait until next absolute 1-tick release
    sample feedback / command snapshot
    compute cascade controller
    apply limits
    advance SIL plant (if plant runs on target)
    publish telemetry snapshot
    record timing counters (not printf per tick)

Thứ tự chính xác cần chốt: ví dụ update sensor → compute command → apply to plant → log. Plant discrete-time index và controller sample phải nhất quán để không tạo trễ giả hoặc “nhìn thấy tương lai”. Một cách phổ biến là controller dùng measurement tại k, output u[k], plant advance từ k sang k+1.

9.2 Priority, preemption và blocking

Kernel config hiện bật preemption, tắt time slicing. Control task priority cao hơn background/network workload để giảm bị trì hoãn; nhưng priority cao không loại bỏ thời gian interrupt, critical section, hoặc CPU hog task. Trong M1 cần ghi rõ priority tương đối thay vì chỉ nói “high”. Tránh block trên queue/mutex/printf trong control path; lấy command non-blocking hoặc snapshot đã chuẩn bị sẵn.

Không gọi printf mỗi tick: UART polling chậm, libc có lock/stack/MPU implications, và logging tự tạo jitter. Ghi binary counters/samples vào buffer có giới hạn hoặc decimate log (ví dụ mỗi N ticks) từ task thấp hơn. Khi buffer đầy, định nghĩa drop policy/counter.

9.3 Task không nên sở hữu mọi thứ

Giữ thuật toán plant/encoder/PID trong C modules độc lập; adapter RTOS chỉ điều phối thời gian và dữ liệu. M1 có thể bắt đầu bằng setpoint step nội bộ để kiểm tra vòng điều khiển, chưa phụ thuộc UDP echo. Khi Comm task thật xuất hiện ở các milestone sau, command sẽ được đưa qua queue/mailbox; không để parser mạng sửa thẳng PID state giữa chu kỳ.

Invariant hữu ích: mỗi control tick có tối đa một command snapshot rõ nguồn gốc; controller state chỉ bị control task sửa; output cuối cùng luôn qua saturation/rate/soft-limit policy; task khác đọc telemetry snapshot nhất quán.

10. MPU: cô lập control task mà không tự khóa mình

M0 đã chứng minh MPU qua [mpu_selftest.c](../freertos/app/mpu_selftest.c): task restricted chạy unprivileged, một vùng dữ liệu RO bị ghi → MemManage. M1 chuyển từ “fault demo” sang task điều khiển thật, nên phải thiết kế quyền bộ nhớ trước khi tạo task.

10.1 Mô hình đặc quyền

  • Privileged task/code có quyền hệ thống rộng hơn; unprivileged task chỉ truy cập code/data/objects được MPU cho phép.
  • FreeRTOS MPU port dùng region descriptors; Cortex-M MPU có yêu cầu kích thước/alignment và số region hữu hạn. Xem giới hạn của port và linker script hiện tại, không sao chép region sample một cách máy móc.
  • Stack control task phải được cấu hình đúng cho MPU port, đủ lớn và được canary/high-water-mark kiểm tra. Buffer/struct global mà task truy cập cũng cần quyền region thích hợp.
  • Không đưa network driver/socket/FreeRTOS heap tùy tiện vào vùng control task. IP/RX task đang chạy privileged do thiết kế M0; control task nên được restricted nhưng chỉ gọi kernel API theo cơ chế MPU wrapper/ACL cho phép.

10.2 Ownership trước shared memory

Phương án an toàn, dễ reasoning: Comm task gửi một command object qua queue; control task nhận non-blocking và copy thành local snapshot. Telemetry được publish bằng queue hoặc double-buffer có quy tắc ownership. Queue là kernel object nên task restricted cần quyền ACL phù hợp với wrapper version hiện bật; kiểm tra access control object thật trong port. Nếu dùng shared struct volatile, nhớ rằng volatile không tự tạo atomicity, mutual exclusion, memory ordering hay snapshot nhất quán.

10.3 Thiết kế fault path

M1 acceptance tập trung control response, nhưng kiến trúc tổng có REQ-SAF-007: HardFault/MemManage phải disable output, lưu fault record vào .noinit, reset và báo sau reboot. Hiện handler M0 còn là self-test/recovery demo; không giả định đã hoàn thành safety path này. Khi mở rộng handler: không gọi FreeRTOS API, socket hay printf; chỉ làm thao tác tối thiểu đã kiểm chứng. Fault cố ý trong self-test không được nhầm thành fault production.

MPU không thay thế design correctness: MPU ngăn truy cập vùng không được cấp, nhưng không phát hiện PID sai, parameter NaN, command cũ, hay control deadline miss trừ khi code chủ động kiểm tra.

11.2 Giới hạn của SysTick và DWT

QEMU 8.2.2 đã kiểm tra: DWT CYCCNT không được model (đọc 0), nên không dùng DWT để tuyên bố cycle timing. configTICK_RATE_HZ=1000 cho tick granularity 1 ms. Nếu chỉ lấy xTaskGetTickCount(), resolution của timestamp là 1 ms — không đủ phân biệt 20 µs với 200 µs jitter trong cùng tick. Histogram khi đó chủ yếu cho biết số tick trễ/overrun, không phải sub-millisecond timing.

SysTick hardware có counter đếm trong một tick; có thể thử ghép tick count với SysTick current-value register để tạo timestamp dưới 1 ms, nhưng cần xác minh clock source, reload, wrap/race quanh tick interrupt trên đúng QEMU/FreeRTOS port. Không ghi nhãn “microsecond accurate” chỉ vì convert count sang µs; phải validate counter increments và behavior khi -icount.

11.3 Lựa chọn đo theo mức độ tin cậy

  1. Bắt buộc và chắc chắn: đếm tick, missed release, execution vượt số tick, số lần deadline miss. Đây là timing quan sát được với độ phân giải 1 ms.
  2. Nếu SysTick VAL được xác minh: tạo timestamp sub-tick nhất quán bằng tick+down-counter; xử lý rollover (đọc tick/counter theo mẫu retry) và xác nhận bằng test interval dài đã biết.
  3. -icount + idle hook: dùng như chỉ số proxy/so sánh độ ổn định CPU rảnh, không gọi là jitter của control task. ulIdleCount thay đổi do workload/scheduler; nó không trực tiếp đo lúc control task bắt đầu/kết thúc.
  4. Host wall-clock: đo thời gian host để báo runtime/throughput SIL; không trộn với virtual tick để pass/fail control deadline.

Định nghĩa metric jitter phải được chốt trong báo cáo: chẳng hạn start lateness t_start[k]−t_release[k]; period jitter (t_start[k]−t_start[k−1])−T; execution time riêng. Đừng gộp 3 chuỗi vào một cột “jitter”. Dữ liệu histogram có thể lưu sample_index,release_tick,start_tick,finish_tick,start_lateness_ticks,execution_ticks,deadline_miss; nếu dùng sub-tick thì thêm đơn vị cụ thể.

Điểm cần chủ động sửa trong hiểu biết/spec: project plan nói “jitter bằng DWT/SysTick”, nhưng DWT không chạy trên model hiện tại. SysTick tick count 1 ms chỉ cho timing thô. M1 phải kiểm tra SysTick down-counter hoặc ghi rõ giới hạn; idle-hook/-icount là proxy chứ không thay phép đo trực tiếp. Kết quả là SIL/virtual timing, không phải hard real-time.

12.1 Test theo invariant, không chỉ snapshot

  • Vị trí/tốc độ/dòng/output phải hữu hạn sau mỗi bước hợp lệ.
  • Output luôn trong amplitude bound và delta mỗi bước không vượt slew limit.
  • Target/trajectory không vượt soft limits theo policy đã chọn.
  • Khi actuator saturation lâu, integral state không phình không giới hạn; đảo lỗi thì output bắt đầu thoát saturation trong thời gian hữu hạn.
  • Cùng config, seed, input sequence → cùng trace (trong tolerance số học đã định nghĩa).
  • Kiểm thử cả boundary và invalid input: R=0, L=0, J=0, N=0, dt≤0, giới hạn min≥max, overflow count.

12.2 Host và Cortex-M3 có thể khác

Host thường dùng double/FPU khác target Cortex-M3. Chọn float/double API rõ ràng; acceptance test có tolerance (absolute/relative) thay vì so bit-exact giữa platform khác nhau. Mọi random sequence cần fixed seed. Nếu target dùng software float, đo tải task sau khi tích hợp; host test nhanh không chứng minh 1 ms deadline đạt trên QEMU.

13. Trình tự làm M1 có kiểm soát

  1. Chốt model contract: quy ước dấu, đơn vị, state, parameter validity, dt, integrator, encoder CPR và semantics stuck.
  2. Viết/test plant trước controller: equilibrium, dấu, response open-loop, kiểm tra dt và hội tụ; chưa cần FreeRTOS.
  3. Viết/test encoder: lượng tử hóa trước, nhiễu reproducible sau, stuck fault độc lập.
  4. Viết PID đơn vòng: state struct/config, saturation, rate limiting, anti-windup; unit-test từng phần.
  5. Ghép cascade offline: position → speed → voltage; tune speed loop trước position loop; tạo step CSV + metrics.
  6. Chốt định nghĩa acceptance: Mp<10%, settling band/duration, test amplitude/config, cách tính jitter. Không đổi tiêu chí sau khi thấy kết quả.
  7. Đưa thuật toán vào task adapter: 1 tick/1 ms, priority, queue/snapshot, overrun counters, không printf từng tick.
  8. Bật MPU có từng bước: task tạo được → đọc state/stack hợp lệ → truy cập object được cấp quyền → negative test vùng cấm.
  9. Đo timing QEMU: tick-level trước; thử SysTick down-counter nếu cần sub-tick; phân biệt execution, release jitter, period jitter, deadline misses.
  10. Build report: chạy Ceedling host tests, firmware build, QEMU scenario, lưu CSV/plot và cấu hình để tái lập.
