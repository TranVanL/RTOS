0 · Cách học và cách đọc guide

Đừng học API theo kiểu thuộc tên hàm. Với mỗi cơ chế, tự trả lời 6 câu: ai sở hữu dữ liệu, thread nào chạy, khi nào block, ai đánh thức, lỗi/timeout đi đâu, đo bằng chứng gì?

  1. Đọc mental model, task lifecycle, scheduler, tick và ISR trước.
  2. Sau đó tự vẽ task graph cho node motion, đánh dấu priority, queue, semaphore, ISR và ownership.
  3. Chạy lab nhỏ: task periodic, queue producer/consumer, ISR notification, stack/heap diagnostics.
  4. Ánh xạ vào project: Comm task nhận frame; Control task tiêu thụ command và chạy vòng 1 kHz; Supervisor kiểm tra alive/watchdog.
  5. Luyện Q&A theo công thức: định nghĩa → cơ chế → trade-off → ví dụ đã chạy → giới hạn chưa chứng minh.
Interview bar: senior-level answer có state diagram, failure path, priority/latency reasoning và test evidence. “Dùng queue vì thread-safe” là câu mở đầu, không phải câu trả lời hoàn chỉnh.

1 · Mental model: FreeRTOS là gì?

FreeRTOS Kernel là một kernel real-time nhỏ, có thể cấu hình, cung cấp task scheduling, queues, semaphores/mutexes, task notifications, software timers và cơ chế đồng bộ. Nó thường chạy bare-metal cùng application và BSP/HAL, không phải một desktop OS: thường không có process/address-space isolation đầy đủ, filesystem, shell hay POSIX environment trừ khi các thành phần riêng được thêm.

Kernel

Ready/block lists, scheduler, tick handling, context switch và primitive đồng bộ.

Port

CPU/compiler-specific context save/restore, interrupt entry, critical-section implementation và tick setup.

BSP / drivers

Startup, clock, UART, Ethernet, watchdog, GPIO; có thể là SDK/vendor code hoặc project code.

Application

Tasks, state machines, protocol, control loop, health supervision và policy khi lỗi.

Kernel không tự làm ứng dụng real-time

FreeRTOS hỗ trợ scheduling ưu tiên; deadline của system vẫn phụ thuộc interrupt latency, task WCET, priority, blocking, memory/bus, driver và workload. Kernel không tự quyết định “task nào phải chạy trước”, “queue đầy thì sao”, “mất command thì motor làm gì” hay “watchdog kick khi nào”. Đó là thiết kế application/system.

Khác biệt quan trọng với QNX: FreeRTOS thường có một address space; task cùng đặc quyền chia sẻ memory. MPU-enabled port bổ sung memory regions/privilege separation nếu CPU và port hỗ trợ. Không đánh đồng FreeRTOS task với QNX process. Priority FreeRTOS thông thường: số lớn hơn = task priority cao hơn; NVIC interrupt priority Cortex-M thì quy ước ngược về số học trên nhiều MCU (số nhỏ hơn thường urgency cao hơn). Hai hệ priority không được so trực tiếp.

FreeRTOS Kernel vs FreeRTOS+TCP

Kernel không bao gồm network stack. FreeRTOS+TCP là library riêng, với IP task, network interface, buffer management, socket API và driver integration. Bật TCP/IP làm đổi memory footprint, task graph, privilege/MPU assumptions và CPU load; phải test cấu hình tích hợp thật, không chỉ build hai demo riêng.

2 · Kernel architecture và luồng thực thi

Scheduler lifecycle

  1. Khởi tạo phần cứng và các object khi scheduler chưa chạy.
  2. Tạo các task cần chạy trước start.
  3. vTaskStartScheduler() khởi chạy scheduler; thường không return nếu idle task/timer task tạo được và scheduler chạy. Nếu return, investigate allocation/config/start failure path.
  4. Task ưu tiên cao nhất ở trạng thái Ready được dispatch; task chỉ chạy khi Running, Ready và đủ điều kiện scheduler/interrupt.

Không khởi động scheduler trước khi vector table, clock/tick, heap và required low-level port setup sẵn sàng. Các chi tiết phụ thuộc port/demo, vì vậy lần đầu hãy theo đúng demo vendor/upstream rồi mới tùy biến.

FreeRTOSConfig.h là hợp đồng cấu hình giữa application và kernel/port. Các option thay đổi API được compile, memory footprint, scheduling semantics, hook và diagnostics. Một macro sai có thể khiến code build nhưng timing/failure semantics khác dự kiến.

Build reproducibility

  • Pin FreeRTOS Kernel commit/tag, compiler version, board/demo source và QEMU version.
  • Record compiler flags, linker script, startup/vector, FreeRTOSConfig.h và feature libraries.
  • Kiểm tra task stack depth parameter: nhiều FreeRTOS task create APIs tính theo StackType_t words, không phải bytes. Verify API/port/version đang dùng.
  • Enable warnings, static analysis/unit tests trên host cho pure logic; giữ integration tests trên đúng port/QEMU.
  • Không tự sửa kernel port assembly nếu chưa hiểu ABI, exception entry và context frame.
Cortex-M3 MPU project có hai nền demo (MPU kernel port và TCP echo) cần tích hợp. “Mỗi demo build riêng” không chứng minh combined firmware đúng privilege, wrapper, MPU regions, linker map hay RAM budget.

4 · Task lifecycle, state và stack

Task là execution context trong FreeRTOS: có TCB (task control block), stack riêng và priority. Tasks thường cùng chia sẻ address space. Task function thường là vòng lặp vô hạn; nếu task tự return, hành vi không nên để mặc định—dùng cleanup rồi delete theo API/policy được hỗ trợ.

Created → Ready → Running ↙ ↘ Blocked (delay / queue / semaphore / notification) Suspended (explicit suspend; không timeout tự unblock) Deleted (resource cleanup tùy allocation mode/idle processing)
StateÝ nghĩaHay bị nhầm
ReadyĐủ điều kiện chạy, chờ scheduler/priority.Ready nhưng chưa chạy không đồng nghĩa task bị block.
RunningĐang được CPU cấp cho task.Single-core thường chỉ một task chạy tại một thời điểm.
BlockedChờ tick timeout hoặc event/object.Task block đúng cách thường tốt hơn polling CPU.
SuspendedBị đưa ra khỏi ready list cho tới khi resume.Không tự thức dậy chỉ vì timeout; dùng cẩn trọng cho control task.
DeletedKhông được scheduler chạy nữa.Dynamic memory reclamation có thể được thực hiện bởi Idle task; không để Idle starvation.

Task design checklist

  • Một trách nhiệm chính/task; define inputs, outputs, priority, period/event và owner data.
  • Ưu tiên block-on-event thay vì loop kiểm tra cờ liên tục.
  • Không dùng long busy loop; nếu cần compute-bound work, chia chunk/checkpoint hoặc phân tích WCET.
  • Task priority không thay cho synchronization; dữ liệu chia sẻ vẫn cần ownership/critical section.
  • Task stack đủ cho deepest call path + ISR/API usage theo port; không chọn bằng “chạy thử một lần”.
  • Tạo task ở startup hay dynamically runtime là trade-off; runtime creation cần policy khi allocation thất bại.

Task notification vs task handle

Task handle là danh tính/điểm tham chiếu tới task; notification là trạng thái/value được gửi tới task đó. Notification thường rẻ hơn queue/semaphore cho one-to-one signaling, nhưng task receiver phải được xác định và semantics value/clear/increment/bits phải rõ. Không sử dụng notification index mà feature/config/version không hỗ trợ.

5 · Scheduler, priority và starvation

Quy tắc nền

  • Task priority FreeRTOS là số nguyên từ 0 tới mức max được cấu hình; trong cách dùng phổ biến, số lớn hơn nghĩa là priority cao hơn. Kiểm tra priority range/API của version/port.
  • Preemptive mode: task priority cao hơn được Ready có thể preempt task thấp hơn tại scheduling point/interrupt exit theo port.
  • Equal-priority time slicing phụ thuộc configUSE_TIME_SLICING và tick/scheduler behavior; không giả định luôn chia CPU công bằng khi tick/config thay đổi.
  • Cooperative mode (configUSE_PREEMPTION=0) thay đổi cách task nhường CPU; API blocking/yield vẫn có vai trò nhưng phải đọc config semantics.
  • Interrupts không phải tasks và có urgency/priority domain riêng ở NVIC.

Priority assignment cho motion node

Chức năngVí dụ tương đốiRủi ro nếu đặt sai
Control 1 kHzHigh task priority, bounded computationQuá cao nhưng block chờ network/mutex → cả system bị kẹt.
Comm / protocolMedium; wake by packet/event, bounded parseQuá thấp → queue/telemetry backlog; quá cao → control jitter.
Safety supervisorPriority dựa reaction budget, run-to-completion nhỏKicks watchdog bất kể health, hoặc chiếm CPU với polling.
Logging / diagnosticsLow, asynchronous, bounded bufferLog blocking/overflow gây interference hoặc mất fault evidence.
Idle taskKernel lowest priorityStarvation làm idle cleanup/hooks không chạy.

Priority inversion

Task low giữ mutex; task high chờ mutex; task medium preempt low và làm high chờ lâu. FreeRTOS mutex cung cấp priority inheritance ở kernel level nhằm giảm inversion cho owner, nhưng inheritance không thay thiết kế lock ordering/critical sections và không áp dụng cho binary semaphore theo cùng semantics. Recursive mutex cũng có semantics riêng.

Không nâng task “supervisor” lên priority cao nhất rồi để nó poll. FreeRTOS task priority cao bị ready liên tục có thể starve hết task thấp, gồm idle/timer/IP task. Thiết kế high-priority task block thường xuyên và làm bounded work.

Scheduling analysis tối thiểu

  1. Liệt kê task period/event, deadline, estimated execution, blocking resource và priority.
  2. Vẽ dependency: control cần data nào? Comm có thể block control không? Supervisor quan sát counter nào?
  3. Định nghĩa overload policy: drop-oldest/drop-newest/coalesce/fault/SAFE_STOP.
  4. Đo response time dưới interrupt, network, logging và fault-injection load.
  5. Kiểm tra starvation, missed deadline, stack/heap/resource exhaustion.

6 · Tick, delay, periodic release và time math

Tick interrupt cung cấp time base/kernel timeout. Với configTICK_RATE_HZ = 1000, tick danh nghĩa là 1 ms; đây không đồng nghĩa mọi task được dispatch chính xác mỗi 1 ms. Tick resolution, clock drift, interrupt masking, higher-priority execution, tick handler work và scheduler state ảnh hưởng wake-up time.

Relative delay vs periodic delay

vTaskDelay(n) block tương đối từ thời điểm gọi; execution time cộng vào chu kỳ loop, tạo drift. Periodic task thường dùng xTaskDelayUntil() hoặc vTaskDelayUntil() tùy version/API compatibility, để tính theo wake time trước đó. Cần check return/value và define nếu task đã trễ hoặc period nhỏ hơn tick resolution.

TickType_t lastWake = xTaskGetTickCount();
const TickType_t period = pdMS_TO_TICKS(1);

for (;;) {
    read_feedback();
    run_bounded_controller();
    update_safe_output();

    // Chọn API đúng version; vTaskDelayUntil là tên phổ biến ở nhiều bản,
    // một số version cung cấp/ưu tiên xTaskDelayUntil.
    xTaskDelayUntil(&lastWake, period);
}
Đo riêng thời điểm task release/dispatch, execution start/end và output update. Delay API không tự báo đầy đủ deadline miss. Nếu vòng điều khiển mất deadline, “catch up” bằng nhiều chu kỳ back-to-back thường sai với controller; chọn skip, use latest sample, degrade hay fault theo control requirement.

Tick conversion và rollover

  • pdMS_TO_TICKS() có thể truncate/round theo integer math; period nhỏ hơn tick resolution có thể ra zero.
  • TickType_t có width hữu hạn và wrap; dùng comparison/delta method an toàn với tick rollover, không so absolute ticks bằng phép toán tùy tiện.
  • Không dùng tick count như wall clock/time-of-day; tick rate và drift không phải precision time protocol.
  • Sub-tick measurement cần hardware timer/cycle counter nếu port/model hỗ trợ và được kiểm chứng.

Jitter, response time, WCET

Jitter là variation của release/response; WCET là bound dưới giả định cụ thể, không phải max thấy trong histogram. Trên QEMU, cycle counter/peripheral timer capability phải xác minh; host scheduling có thể làm thời gian wall-clock khác với virtual CPU cycles. Báo rõ clock source, units, QEMU command, host load, sample count và workload. p99 < 50 μs trong QEMU là SIL metric, không phải silicon guarantee.

7 · ISR, NVIC và API FromISR

ISR xử lý ngắn và bounded: xác định/ack nguồn theo datasheet, capture tối thiểu, đánh thức task; phần parse/control/heap/logging làm ở task context. ISR có urgency cao hơn tasks, nhưng Cortex-M priority numbering và FreeRTOS priority numbering khác nhau.

ISR-to-task handoff

Peripheral event → NVIC interrupt → ISR: clear/ack + capture minimal data → xQueueSendFromISR / vTaskNotifyGiveFromISR / semaphore FromISR → set higher-priority-task-woken flag → request portYIELD_FROM_ISR() / portEND_SWITCHING_ISR() → exception return / PendSV context switch (port-specific)

Rules for ISR-safe calls

  • Dùng API có hậu tố FromISR khi gọi từ ISR; API task-context có thể block nên không gọi trong ISR.
  • Thường thời gian block bằng 0 trong FromISR APIs; nếu queue full, xử lý fail theo policy, không spin trong ISR.
  • Truyền biến xHigherPriorityTaskWoken nếu API yêu cầu; request context switch ở cuối ISR theo macro port.
  • Chỉ gọi FreeRTOS API từ interrupt có priority hợp lệ theo port config. Interrupt urgency cao hơn ngưỡng syscall thường không được gọi API kernel.
  • Đảm bảo NVIC priority bits, priority grouping, CMSIS vs raw shifted priority constants thống nhất.
  • Không disable interrupt dài để “bảo vệ” struct lớn; dùng atomic/critical section ngắn hoặc ownership queue.
Lỗi interview/bring-up phổ biến: đặt NVIC interrupt priority quá cao (số thấp/urgency cao) nhưng gọi xQueueSendFromISR(), gây assert/corruption trên một số port. Đọc comment trong đúng portmacro.h và config; phân biệt configMAX_SYSCALL_INTERRUPT_PRIORITY đã shifted với configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY unshifted nếu port/CMSIS cung cấp cả hai.

ISR latency & nesting

Latency phụ thuộc interrupt mask/BASEPRI, higher-urgency ISR, exception stacking, flash wait-state, bus contention và port. Cortex-M3 có NVIC/vector priorities, nhưng đo trên QEMU không nhất thiết đại diện silicon implementation. Interrupt nesting và stack usage cần được tính cho MSP/handler stack; task stacks không bao quát mọi exception stack use.

Queue-by-copy và pointer ownership

Queue copy những item bytes có kích thước đã cấu hình; nếu item là pointer thì chỉ pointer được copy, không phải object đích. Pointer phải trỏ tới lifetime hợp lệ; định nghĩa producer→queue→consumer ownership, release/reuse, full-queue policy và cancellation. Không gửi pointer tới biến stack của task producer.

Latest value vs event FIFO

Control setpoint thường cần “mới nhất hợp lệ”, không nhất thiết xử lý hết mọi command cũ. Có thể dùng queue length 1 với overwrite API hoặc mailbox/double-buffer thiết kế cẩn thận; nhưng E-stop/fault event không nên bị silently overwritten. Phân loại message: state snapshot, command transaction, event/fault; chọn semantics mỗi loại.

Queue capacity là design parameter

Ước lượng arrival burst, consumer blackout, item size và maximum delay. Theo dõi high-water mark/dropped count. Queue dài không giải quyết consumer starvation—nó chỉ trì hoãn lúc full và tăng command age. Set queue full behavior tường minh, test burst/backpressure.

9 · Mutex, semaphore, critical section và deadlock

Mutex vs binary semaphore

  • Mutex: resource ownership; task lấy/nhả; FreeRTOS mutex có priority inheritance semantics.
  • Binary semaphore: synchronization token; có thể được give từ ISR bằng FromISR API; không phải mutex và không có PI ownership.
  • Counting semaphore: đếm resource/event capacity.
  • Critical section: port-specific interrupt/critical mechanism cho vùng cực ngắn; không bao I/O/loop dài.

Priority inheritance: giới hạn thực tế

PI tạm nâng mutex holder khi task priority cao bị block để giảm unbounded inversion do medium task. Nó không ngăn deadlock, không sửa lock hierarchy, không bảo đảm thời gian giữ lock và không giúp khi high task block trên queue/network/driver. Nested mutex behavior và disinheritance details phụ thuộc kernel implementation; review source/version nếu critical.

Deadlock prevention

  1. Vẽ lock ordering toàn ứng dụng, luôn lấy locks cùng thứ tự.
  2. Tránh lock qua queue wait, socket receive, log/file, timer callback hoặc gọi code ngoài ownership.
  3. Giữ mutex bảo vệ state invariant trong thời gian ngắn, không chạy PID/plant trong critical section nếu không cần.
  4. Không suspend/delete task đang giữ mutex trừ khi có recovery contract; owner death có thể để resource unusable.
  5. Phát hiện bằng trace/diagnostics và timeout ở cấp application, nhưng timeout không thay fix deadlock.
Ví dụ: Comm task parse frame thành command local rồi enqueue; Control task copy/consume snapshot tại boundary rõ ràng. Tránh Control task lock mutex mà Comm giữ trong lúc chờ socket—nếu không, network delay biến thành control jitter.

10 · Memory: heap, stack, static allocation

Trong embedded, memory management là behavior của firmware, không phải việc để “OS tự lo”. Phải biết stack nào nằm ở RAM nào, heap scheme nào được compile, object nào dynamic, allocation failure ra sao, và buffer lifetime thế nào.

Các heap implementation thường được cung cấp trong source distribution có khác biệt về coalescing, freeing, multi-region support và determinism. Không nói “heap_4 luôn dùng trong project” khi chưa kiểm tra Makefile/link map/config; ghi rõ file heap nào thực sự compile.

Task stack

  • Stack depth API thường tính theo số phần tử StackType_t, thường tương ứng words, không phải bytes; verify typedef/port.
  • Call depth, local arrays, nested library calls, FPU state (nếu core có FPU), exception path/port frame và compiler optimization ảnh hưởng stack.
  • uxTaskGetStackHighWaterMark() hữu ích cho observed minimum free stack, nhưng không phải static proof; check units/version API.
  • configCHECK_FOR_STACK_OVERFLOW modes/hook chỉ phát hiện một số class overflow; có thể phát hiện muộn hoặc không bắt mọi corruption.
  • Stack overflow hook phải xử lý tối thiểu; nếu stack đã hỏng, không tin các local variables/printf/locks.

Heap and buffer diagnostics

  • Bật configASSERT, malloc-failed hook và stack checks trong debug; hook phải được compile và link.
  • Record free heap, minimum-ever-free, largest free block nếu heap implementation cung cấp.
  • Kiểm tra integer overflow ở kích thước allocation; zeroize/ownership nếu dữ liệu cần.
  • Use static buffer pool hoặc fixed-size block pool khi muốn predictable bounded allocation.
  • Guard against queue buffer overrun, DMA alignment/cache requirements (đặc biệt trên MCU khác Cortex-M3).

11 · MPU port: privilege, memory regions và giới hạn isolation

MPU (Memory Protection Unit) áp dụng access permissions cho vùng memory; không giống MMU đầy đủ với virtual address translation. FreeRTOS MPU port có thể chạy một số task ở unprivileged mode và gán region access, trong khi kernel/privileged tasks được quyền rộng hơn. Cụ thể phụ thuộc CPU (M3), port implementation, MPU region count/alignment, memory map và wrapper/syscall design.

MPU task model

  • Task có code, stack và configured user regions được phép truy cập; mọi region còn lại bị cấm theo policy.
  • Privileged task/code có quyền cao hơn; chạy TCP/IP stack/driver privileged có thể đơn giản integration nhưng làm giảm isolation.
  • System calls/wrappers cho unprivileged task phải validate pointer/length và chuyển vào privileged kernel safely.
  • MPU regions có alignment/size/number constraints; overlapping region priority/subregion rules cần đọc ARMv7-M and port docs.
  • MPU violation thường raise MemManage fault; handler/reset behavior và ability to recover phải được thiết kế.

Không nên claim quá mức

MPU không tự bảo vệ trước privileged-code bug, DMA/peripheral masters (nếu có), shared buffer misuse, TOCTOU, logic corruption hay attack model mà MPU không bao phủ. “Control task isolated” chỉ đúng nếu linker regions, task config, wrappers, context switch và negative tests đều khớp. MPU isolation không đồng nghĩa memory-safe language hoặc safety certification.

Project-specific integration questions

  • Đang dùng đúng ARM_CM3_MPU port (not standard ARM_CM3) trong final linked image chưa?
  • Task create API nào và task parameter/region definition đúng port revision chưa?
  • Kernel objects, FreeRTOS+TCP buffers/socket calls có accessible memory region không?
  • TCP/IP task chạy privileged hay unprivileged? Vì sao? Có wrapper/MPU config nào chứng minh?
  • ISR có privileged execution semantics ra sao? Buffer truyền ISR→task được map/access thế nào?
  • Negative tests: control task đọc/ghi unauthorized region → fault capture; safe output action thật sự khả thi ở fault context chưa?

Project plan đã xác định MPU + FreeRTOS+TCP integration là risk gate: nếu stack/driver privilege xung đột, có thể giữ network stack privileged và cô lập control/comm task. Đây là trade-off nên nêu minh bạch, rồi giảm quyền tối đa trong giới hạn port, không giả vờ toàn bộ task đều isolated.

12 · Software timers, timer service task và event loops

FreeRTOS software timers được xử lý bởi timer service/daemon task. API timer thường gửi command tới timer command queue; callback chạy trong context timer service task, không phải ISR và không phải một thread riêng cho từng timer.

Hệ quả thực tế

  • Callback cần ngắn, bounded, không block và không gọi API cần block; nếu callback lâu, các timer khác cũng bị trễ.
  • Timer command queue có capacity; start/reset/stop command có thể fail nếu queue đầy hoặc scheduling/resource issues tùy API return.
  • Timer service task priority và stack là cấu hình quan trọng; đặt quá thấp gây timer lateness; quá cao và callback nặng gây starvation.
  • Auto-reload callback và daemon scheduling không thay cho hard-periodic control loop nếu yêu cầu latency cao.
  • Timer callback có thể notify task để task xử lý phần nặng.

Chọn timer vs task delay

Periodic control thường dùng dedicated task + periodic delay hoặc hardware timer/ISR release tùy timing needs. One-shot timeout/event debounce có thể hợp software timer. Heartbeat check có thể là supervisor task periodic. Chọn theo granularity, latency, callback cost và failure semantics; measure actual release jitter.

13 · Cortex-M3 exception/context-switch internals

Ở Cortex-M, FreeRTOS port gắn scheduler với kiến trúc exception. Cấu trúc phổ biến: SysTick (hoặc timer khác) tạo kernel tick; PendSV thực hiện context switch ở mức thấp; SVC được dùng để start scheduler hoặc privileged system-call paths tùy port. Không hard-code các chi tiết nếu port chọn timer/handler khác.

Task running (Thread mode) ↓ SysTick/timer exception kernel updates tick / unblocks delayed tasks ↓ if context switch needed PendSV pending (lowest urgency by design in common Cortex-M ports) ↓ save outgoing context, select next Ready task, restore context exception return → next task executes

MSP, PSP, exception frame

  • Cortex-M có Main Stack Pointer (MSP) và Process Stack Pointer (PSP); FreeRTOS task context thường dùng PSP còn handler mode dùng MSP theo port conventions.
  • Hardware automatically stacks part of exception frame; port saves/restores additional registers and task state.
  • Vector table, initial stack, startup code, linker script, FPU configuration (nếu relevant) và compiler ABI phải tương thích.
  • ISR stack/MSP và per-task stack budgets là hai vùng khác nhau; check cả hai.
  • HardFault/MemManage handler debug: stacked PC/LR, exception status registers theo core; xác minh frame format/EXC_RETURN trước khi decode.

Critical sections và BASEPRI

ARMv7-M Cortex-M3 có BASEPRI để mask một dải priority interrupts ở nhiều FreeRTOS ports; implementation cụ thể nằm trong port. Interrupt urgency cao hơn syscall threshold có thể vẫn chạy trong kernel critical section nên không được gọi API kernel. Không tự thay NVIC priority/grouping sau scheduler start mà không hiểu port constraints.

QEMU MPS2-AN385

QEMU mô phỏng Cortex-M3 system/peripheral set của MPS2-AN385; firmware có thể test kernel/task/MPU và một số modeled NIC/watchdog behavior. Model không bảo đảm mọi timing, hardware edge case, cache/electrical behavior hay peripheral detail như silicon. Tài liệu phải ghi QEMU version, machine args, peripheral model và fallback nếu test không supported.

14 · FreeRTOS+TCP, network task và MPU boundary

FreeRTOS+TCP là TCP/IP stack riêng, tích hợp network interface driver và buffer management với kernel. Application task gọi socket-like API; IP task xử lý protocol work theo library design. Network events có thể đánh thức application; application không nên giả định packet processing là zero latency hoặc network API luôn non-blocking.

Node integration model

NIC model (QEMU LAN9118) → interrupt / driver path → FreeRTOS+TCP buffer + IP task → UDP socket receive / protocol validation → Comm task: E2E checks + bounded decode → command queue / latest-setpoint mailbox → Control task (1 kHz) Control/telemetry → bounded outbound queue → Comm/IP task → NIC

Failure/overload design

  • Bound packet size, queue length, receive loop work and command age.
  • Drop malformed/stale datagrams; track counters without logging synchronously in high-priority control.
  • Separate E-stop application message path if architecture calls for it, but UDP loss still exists; local command timeout is essential.
  • Define socket timeout/blocking behavior and ensure Comm task cannot block while holding control mutex.
  • Network stack RAM cost includes buffers, descriptors, tasks/stacks and TCP state; budget link map/heap.
  • Use checksum/counter/data ID/timeouts for E2E error detection as designed; CRC is not authentication.

MPU and network stack

Integrating a privilege-aware MPU port with TCP/IP requires audit of stack task privilege, API wrappers, buffer memory permissions, driver/ISR access and network buffer lifetime. If the example stack expects privileged access, either configure it appropriately or isolate only selected application tasks; document exact boundary and prove with tests. Don't assert “all tasks unprivileged” without verified build/runtime evidence.

Protocol precision in this project

Motion messages are CAN-FD-compatible application frames over UDP, not physical CAN FD. UDP has no arbitration, ACK, bus-off, CAN error frames or physical signaling. Network loopback and QEMU NIC tests validate software integration only within the model.

15 · Motion control 1 kHz: real-time task design

Control task period is 1 ms in the project model. At each activation it should consume a coherent, fresh sensor/setpoint snapshot, run bounded controller math, apply clamps/safety guards and update modeled output. Do not mix socket receive, large logs, dynamic allocation or unbounded waits into this loop.

Cascade PID conceptual flow

valid target + mode → position error → position controller → velocity setpoint (clamp/rate limit) → velocity feedback/error → velocity controller → effort command → saturation + anti-windup + safety limits → actuator-enable model / plant integration → encoder quantization/noise → feedback
e[k] = r[k] − y[k] | u_raw = Kp·e + Ki·Σe·Ts + Kd·(e[k]−e[k−1])/Ts

Formula is conceptual; derivative-on-measurement, filtering, discrete integration method, scaling/fixed-point, saturation order and anti-windup variant are design decisions. Keep controller logic pure/testable on host; make timing-dependent layer small.

Control-loop checklist

  • Single writer owns actuator/control state; Comm task delivers validated commands, not directly writes control variables.
  • Define sample age, sequence, units, scaling, limit and behavior on invalid/missing measurement.
  • Use deterministic numeric ranges; test divide-by-zero, overflow, NaN/Inf if float, saturation and integrator windup.
  • Use fixed sample time in algorithm; detect actual late activation and choose safe response.
  • Plant model and encoder model are simulation only; state units and integrator stability documented.
  • Record setpoint/feedback/output at bounded rate; logging must not change loop period materially.
  • Response quality metrics: overshoot, rise/settling time, steady-state error; real-time metrics: release jitter, execution duration, deadline miss.

Queue policy for commands

For periodic setpoints, a deep FIFO may make control execute obsolete commands. Consider latest valid target mailbox and separate latched events for E-stop/fault. Include command sequence and mode/epoch to reject stale data. If a command is transactional (ENABLE/RESET), preserve acknowledgement and idempotency semantics separately from a setpoint stream.

16 · Fault handling, watchdog and safe output

Watchdog as progress contract

Watchdog kick should indicate the system has made required progress, not merely that a low-priority timer task woke up. Supervisor can check per-task alive counters/deadlines/health reports, verify task progress window and kick only when all required conditions pass. A counter set from code that never runs in normal control path is weak evidence.

Fault handler rules

  • Keep exception/fault code tiny, deterministic, and free from scheduler-dependent operations.
  • Do not call normal queue/socket/printf/heap APIs from HardFault/MemManage context unless explicitly documented safe for that exact path.
  • Capture minimal register/fault metadata into known valid storage; verify `.noinit` linker placement and reset retention semantics.
  • For actual hardware, physical safe output may require external gate/driver circuitry; a software flag in RAM is not proof power stage disabled.
  • On next boot report prior fault record with version/magic/checksum/valid marker; avoid accepting corrupted stale record.
QEMU watchdog behavior is a model-specific result. The project docs cite CMSDK APB watchdog NMI then reset behavior; verify exact QEMU build, machine options and watchdog registers. Don't generalize this to real silicon or claim independent safety without hardware test.

18 · Áp dụng vào QNX–FreeRTOS project

Task graph gợi ý (xác nhận sau khi build demo tích hợp)

[E-stop / safety event task] ← high urgency, bounded, local latch ↓ [Control task: 1 kHz] ← latest validated command + coherent feedback ↑ [Comm task: network receive / E2E / telemetry] ← FreeRTOS+TCP IP task + NIC model ↑ [Supervisor task: health deadlines / watchdog gate] ← alive reports ↓ [Idle task / low-priority diagnostics] ← CPU idle estimate, no blocking hook

Đây là decomposition mục tiêu, không phải assertion rằng code hiện tại đã được triển khai. Task priorities, privileges, stack sizes, queues và timer configuration phải lấy từ final source/config.

Project-specific design decisions

  • Command path: UDP receive → validate magic/length/ID/E2E/counter/freshness → decode bounded signal → command mailbox/queue.
  • Control ownership: Control task is sole writer of controller state and output model; Comm task only publishes valid command snapshot.
  • E-stop: latched state has precedence over all later ENABLE/target commands; separate UDP socket is prioritization, not guaranteed delivery.
  • Heartbeat: alive counters tied to actual progress/deadline, not simply periodic increment by supervisor.
  • Watchdog: kick only after required task health; no kick when control misses defined progress condition.
  • Telemetry: decimate/coalesce under overload; avoid queueing stale position samples indefinitely.
  • MPU: state exact regions and privileged tasks; explicitly describe TCP/IP task privilege trade-off and test inaccessible region.
  • Metrics: QEMU peripheral counter only if implemented and stable; otherwise label timer source and measurement resolution honestly.

Definition of done for the FreeRTOS node

  1. Build reproducibly with recorded source revisions and kernel config.
  2. Tasks, priorities, stack sizes and owners documented; no unexplained busy loops.
  3. Unit tests cover PID/plant/E2E/FSM edge cases on host.
  4. QEMU validates MPU negative path, watchdog model, NIC receive/send, task stall and restart behavior.
  5. Control loop report contains timing and response metrics with SIL caveat.
  6. Fault reaction is measured end-to-end from injection to model output, not inferred from configured timeout alone.
Project interview trap: “QEMU Cortex-M3 with MPU” is not equivalent to motor hardware plus certified safety. Be precise: kernel, port and modeled peripherals run; plant/encoder/output are software models; UDP frames are not physical CAN; the timing numbers characterize the SIL configuration.

19 · 60 câu hỏi FreeRTOS (kèm khung trả lời)

Mỗi câu trả lời tốt nên có cơ chế + failure mode + bằng chứng. Dùng nút trên đầu trang để mở/tắt toàn bộ.

A. Kernel and task model

1. FreeRTOS là gì, và không phải là gì?
FreeRTOS Kernel là embedded RTOS kernel có task scheduler và synchronization primitives. Nó không tự là full OS/process isolation/network stack; middleware/BSP/application là các thành phần riêng. Project dùng FreeRTOS Kernel với MPU port và FreeRTOS+TCP.
2. Task khác process thế nào?
FreeRTOS task là scheduling context trong cùng address space theo mặc định. MPU port có thể hạn chế memory access nhưng không tạo process/MMU isolation hoàn chỉnh như QNX/Linux.
3. Ready, Running, Blocked, Suspended khác nhau?
Ready đủ điều kiện chạy; Running đang chiếm CPU; Blocked chờ event/timeout; Suspended bị explicit suspend và không tự timeout-unblock. Phân biệt task không được schedule vì priority với task đang block.
4. Scheduler bắt đầu khi nào?
Application tạo objects/tasks rồi gọi vTaskStartScheduler(). Scheduler tạo idle/timer service task theo config và dispatch highest-priority Ready task. Nếu return, điều tra heap/stack/config/port initialization.
5. FreeRTOS priority number có nghĩa gì?
Thông thường số cao hơn là task priority cao hơn, index dưới configMAX_PRIORITIES; verify API/config. Không nhầm với Cortex-M NVIC priority encoding hay QNX priority scale.
6. Preemptive và cooperative scheduling khác nhau?
Preemptive config cho phép higher-priority Ready task thay current task tại scheduling points/interrupt exit. Cooperative config đổi preemption behavior; tasks phải yield/block theo semantics. Xem configUSE_PREEMPTION và port.
7. Equal-priority tasks có time slicing không?
Có thể được chia tại tick khi time slicing/config phù hợp; phụ thuộc configUSE_TIME_SLICING, preemption và port. Không coi đây là fairness guarantee cho tasks luôn Ready.
8. Idle task làm gì?
Kernel background task; có vai trò cleanup memory của deleted tasks trong dynamic allocation use, có thể chạy idle hook. Nếu high-priority tasks never block, idle bị starve và cleanup/hook không chạy.
9. Có nên delete task?
Có thể dùng khi lifecycle yêu cầu, nhưng object/stack allocation mode và reclamation behavior cần rõ. Không delete task đang giữ mutex/resource mà không có recovery/ownership cleanup.
10. Task function return thì sao?
Thiết kế task loop/lifecycle rõ; không dựa vào return behavior tùy ý. Gọi cleanup rồi vTaskDelete(NULL) nếu đúng policy/version; handle resource release.

B. Timing, scheduler and ISR

11. vTaskDelay vs vTaskDelayUntil?
vTaskDelay relative delay sau khi gọi, nên work time gây drift. Delay-until API dựa wake time absolute/periodic; API naming/return differences tùy version. Detect lateness and define overrun policy.
12. Tick rate 1000 Hz có nghĩa gì?
Nominal tick 1 ms, không đảm bảo task dispatch exactly mỗi millisecond. Higher priority work, ISR, critical sections, timer resolution và clock drift ảnh hưởng response/jitter.
13. pdMS_TO_TICKS có pitfall gì?
Integer conversion có thể truncate; duration nhỏ hơn resolution ra zero; tick type wraps. Check tick rate, type width, rollover-safe comparisons and API return.
14. Jitter khác execution time thế nào?
Jitter là variation release/response time; execution duration là time from start to finish. Đo riêng activation interval, response, compute duration and deadline miss.
15. Histogram max có chứng minh WCET không?
Không; đó chỉ là maximum observed sample trong một setup/workload. WCET bound cần analysis/coverage/assumptions and target-specific evidence. SIL data useful for regression, not silicon certification.
16. Khi nào gọi API FromISR?
Trong ISR dùng only documented FromISR API; không gọi blocking task API. Check return, queue-full path, higher-priority-task-woken and yield macro at ISR exit.
17. configMAX_SYSCALL_INTERRUPT_PRIORITY là gì?
Port threshold xác định mức NVIC urgency nào được gọi FreeRTOS API trong ISR; exact polarity/encoding varies. Check portmacro/config/CMSIS representation and priority grouping.
18. Vì sao không log/printf trong ISR?
Potentially unbounded, blocking, non-reentrant and high latency; can corrupt shared state or exceed interrupt budget. Capture minimal data and defer to task.
19. ISR có thể preempt task không?
Interrupt execution is separate from task scheduler; NVIC priority/nesting/critical masks control interrupt preemption. On ISR exit, kernel may request a context switch to a newly-ready higher task according to port.
20. Tickless idle dùng để làm gì?
Suppress periodic ticks during idle to reduce power when supported; port compensates elapsed time. It affects wake/timing behavior and requires correct low-power timer/clock integration. Verify project config/port; not relevant automatically to all targets.

C. Queues, notifications and synchronization

21. Queue có copy data không?
Queue copies item bytes of configured size. If item is a pointer only pointer is copied; lifetime/ownership remains application responsibility. Avoid stack pointer escapes.
22. Queue vs task notification?
Queue for messages/FIFO/multiple producer-consumer data. Notification for efficient task-targeted signaling/count/value/bits; semantics single recipient task. Use API's clear/increment/overwrite mode intentionally.
23. Task notification có thể thay semaphore không?
For many one-task event/count use cases yes, efficient; but not universally. Need consider multiple waiters, ownership, API semantics/index and observability. Mutex/queue/event-group semantics differ.
24. Stream buffer assumptions?
Typically optimized for one writer and one reader; byte stream has no message boundary. Multiple writers/readers require external serialization or another primitive. Verify exact version docs.
25. Queue full thì làm gì?
Define per-message policy: block with bounded timeout, reject, drop newest/oldest, coalesce latest state, or fault. Track high-water/drop counts; never wait indefinitely in high-priority control path.
26. Mutex khác binary semaphore?
Mutex has ownership and priority inheritance behavior; binary semaphore is synchronization token and can be given from ISR using FromISR. A binary semaphore does not provide mutex ownership/PI semantics.
27. Priority inversion là gì?
Low task holds mutex; high task blocks on it, medium task preempts low so high indirectly waits. Mutex PI can boost owner; still need short critical sections, lock order and bounded blocking.
28. Có thể take/give mutex từ ISR không?
No normal mutex ownership operations from ISR; use appropriate FromISR semaphore/notification APIs. Mutex owner must be task context.
29. FreeRTOS mutex PI có giải quyết deadlock không?
No. It mitigates some priority inversion, not cyclic lock dependencies, owner failure or unbounded hold times. Use lock hierarchy and avoid blocking while holding mutex.
30. Event group có giữ từng event occurrence không?
Event bits represent state; repeated same bit sets coalesce. Not a FIFO of event occurrences. Use queue/counter if each occurrence matters.

D. Memory, MPU, port and config

31. Stack depth xTaskCreate tính bằng byte?
Common FreeRTOS APIs specify depth in words/StackType_t units, not bytes; exact API/port version must be checked. Convert and calculate actual stack bytes accordingly.
32. Stack high water mark có đủ chứng minh stack safe?
No, it's an observed minimum free stack during tested path, not proof of untested worst-case. Combine static call-depth/stack analysis, stress paths, guard/check hooks and margin.
33. heap_1..heap_5 khác nhau?
They are alternative heap implementations with differing allocation/free/coalescing/multi-region behavior; selected source matters. Don't assume a heap scheme from FreeRTOSConfig alone—inspect build/link map and test fragmentation/allocation failure.
34. Static allocation có ưu điểm gì?
Predictable storage/lifetime and no runtime heap fragmentation for those objects; requires compile-time sizing and static APIs/config. Dynamic remains useful but needs deterministic failure handling and budget.
35. configCHECK_FOR_STACK_OVERFLOW catches all overflow?
No. Check modes are implementation-specific and detection can be late/incomplete; guard patterns can be overwritten beyond detection. Use robust sizing/analysis and fault tests.
36. MPU vs MMU?
MPU enforces access permissions on regions without general virtual address translation; MMU supports virtual memory mapping/page-level mechanisms. FreeRTOS MPU port reduces selected task access; it does not create full process isolation.
37. MPU violation handler should do what?
Minimal capture of valid fault state and force a defined safe/fail-stop action if permitted. Avoid normal FreeRTOS APIs, heap, printf or locks in corrupted exception context. Then reset/contain according to recovery policy.
38. Port layer responsible for what?
CPU-specific context save/restore, scheduler start, tick/interrupt wiring, critical sections and port macros. Verify exact compiler/CPU/MPU port and never mix incompatible port files.
39. Why can MPU demo plus TCP demo fail to integrate?
Different privilege assumptions, API wrappers, buffer regions, interrupt/network driver, heap/stack layouts, configuration and source versions. Validate final combined image and task access, not each standalone demo only.
40. configASSERT helps how?
Turns assumptions/config violations into early diagnostic failure in debug, such as invalid ISR priority. It must be defined and active; production reaction should not rely on assertion alone.

E. Timers, watchdog, networking and control

41. Software timer callback runs in ISR?
No; timer service/daemon task runs callbacks in task context. Callbacks should be short and non-blocking; long callback delays other timer processing.
42. Timer command queue full?
Timer API command may fail/queue not be serviced; check return and size/priority/daemon health. Do not assume a start/stop command took effect without verifying API contract.
43. Watchdog should be kicked by which task?
A supervisory path after checking required task progress/health, not an unconditional periodic task. Define what evidence means alive and what happens if a task stalls.
44. Why watchdog reset isn't a safety system by itself?
It detects selected no-progress failures after timeout; doesn't guarantee output safe before reset, detect all corrupt states, or provide independent hardware shutdown. Need fault model and safe output path.
45. UDP command reception should happen in control task?
Usually separate bounded Comm/IP work from 1 kHz control. Validate and publish coherent command snapshot; control task consumes without blocking on network. Exact decomposition depends measured load.
46. CRC-32 authenticates UDP command?
No. CRC detects certain accidental corruptions; it is not cryptographic authentication and doesn't prevent replay/spoofing. Counter/freshness and auth are separate concerns.
47. How keep control task from consuming stale queue entries?
Define whether setpoints are latest-value or event FIFO; use bounded queue/mailbox with sequence/age validation and suitable drop/coalesce policy. Safety commands/faults need separate latched/event path.
48. Anti-windup có tác dụng gì?
Prevents integral term continuing to accumulate when output saturates, which can cause long recovery/overshoot. Choose strategy (clamp/back-calculation etc.) and test limits/step changes, not just nominal response.
49. Dùng float PID có luôn ổn định hơn fixed-point?
No. Depends MCU FPU (Cortex-M3 typically no hardware FPU), compiler/runtime cost, numeric range, deterministic execution, scaling and precision. Measure execution and test quantization/overflow. In M3 software float may add cost.
50. FreeRTOS on QEMU validates what?
Kernel/task/port behavior and modeled peripherals within configured emulation, useful for reproducible functional tests. It doesn't prove real hardware timing/electrical/peripheral corner cases or product safety certification.

F. Project and system-design rounds

51. E-stop arrives during ENABLE command—who wins?
Define latched ESTOP invariant and single owner/serialization; all enable commands check latch/state/epoch at commit. E-stop must dominate stale/reordered command. Test races and reset/re-enable authorization.
52. Comm task crashes—what happens?
Control uses freshness of last valid command; after timeout enters defined safe output; supervisor sees missed progress and stops watchdog kick if required. Recovery rejects stale state and reconciles sequence/session before re-enable.
53. Control task doesn't meet 1 ms period—what do you investigate?
Measure release and execution separately; inspect higher-priority tasks/ISR, critical-section time, queue/mutex blocks, network/log load, math cost, compiler and QEMU host/virtual clock effects. Classify miss and apply control-specific policy.
54. How do you prove task isolation with MPU?
Show final port/config/link map and region permissions, demonstrate negative read/write tests, capture fault outcome and verify unaffected components/safe behavior. State which tasks remain privileged and limitations.
55. How do you size a queue?
Based on producer burst/period, consumer service rate, longest expected blackout and acceptable data age; instrument high-water/drops; fault test burst. Larger queue can increase latency/stale commands and doesn't solve sustained overload.
56. How do you test watchdog gating?
Make one critical task stop reporting progress while supervisor remains runnable; verify kick ceases, exact watchdog behavior occurs, fault record preserved and reboot path doesn't enable output prematurely. Also test false-positive threshold under load.
57. Why split unit tests and QEMU tests?
Pure math/protocol/state logic runs fast on host with deterministic unit coverage; QEMU covers port/kernel/peripheral integration. Hardware still needed for actual board timings and hardware electrical behavior.
58. What if fault handler calls FreeRTOS queue API?
Potential scheduler/lock/stack corruption and non-reentrant behavior in fault context. Keep it minimal, store bounded fault record and defer reporting to reboot/recovery path unless exact API/port explicitly supports it.
59. What's the most important SIL limitation in your project?
Timing/peripherals are model-specific: no physical motor/CAN FD/silicon watchdog and host virtualization affects time. Clearly separate validated logic/integration from hardware assumptions; define next HIL/board verification.
60. Explain your FreeRTOS architecture in 90 seconds.
State node role, task graph, priority and data ownership; show command-to-control path, local timeout/watchdog, MPU boundary and tests. Finish with measured SIL evidence and limitations. Avoid listing APIs without explaining why.

VinSurgical · trọng tâm FreeRTOS

  • Task decomposition, priority assignment, deadline/jitter, blocking analysis và control-loop design.
  • ISR-to-task communication, NVIC priority constraints, queue and notification ownership.
  • Stack/heap budget, MPU task regions, privileged vs unprivileged trade-offs.
  • Watchdog health contract, local fail-safe, ESTOP precedence, fault record and reset recovery.
  • Motor PID cascade, saturation/anti-windup, encoder noise/stuck detection, target limits.
  • Verification: requirements traceability, code review, static/unit/integration tests, fault-injection evidence.
VS1. Một task control ở priority cao nhất có phải luôn tốt nhất?
Không. Nếu nó busy-loop/block chờ network/mutex, nó có thể starve Comm/health supervision/idle. Chọn theo deadline and blocking analysis; control task nên làm bounded work, consume snapshot without unbounded wait, then delay until periodic release. Measure end-to-end response.
VS2. Làm sao nói về safety khi project chỉ SIL?
Trình bày safety-inspired mechanisms (local command timeout, latched ESTOP logic, watchdog gating, fault injection) và evidence trong QEMU. Nêu rõ actuator là model, UDP không phải safety bus/hardware E-stop, chưa có hazard-certified product process. Với sản phẩm thực, follow risk management/requirements lifecycle/team safety case, không claim compliance.
VS3. Nếu encoder bị stuck nhưng task vẫn alive thì watchdog có phát hiện?
Không tự động. Watchdog detects progress, not correctness. Need plausibility checks: command vs measured motion, sensor freshness/counter, stuck threshold and state policy. Health report must include semantic checks not merely task heartbeat.
VS4. RESET_FAULT khi nguyên nhân chưa clear?
Reject/retain latch. Verify cause absent, self-tests pass, node states reconciled, authorization and explicit re-enable required. Reset request must not erase evidence or enable actuator accidentally.
VS5. Làm sao chứng minh không bị queue backlog?
Measure queue depth/high-water and item age under burst, consumer stalls and CPU load. Set bounded capacity and overflow policy; stale setpoints coalesce, but E-stop/fault latches preserved. Include test artifact and limit.
VS6. FreeRTOS MPU có thay safety analysis được không?
No. MPU supports memory access separation; doesn't prove functional safety, fault coverage, independent shutdown or absence of privileged bugs. It is one design mechanism whose regions/wrappers/failure response require verification.

VinSpace · kỹ năng chuyển tiếp và telemetry/networking

Trong JD project brief, Linux BSP/Yocto/Device Tree/kernel-driver được cover ở project/công việc khác; ở đây hãy dùng FreeRTOS/QNX để chứng minh embedded concurrency, resource budgets và protocol discipline. Rõ ràng phần nào chuyển giao, phần nào platform-specific.

VX1. FreeRTOS skill nào chuyển sang Embedded Linux?
Concurrency, ownership, bounded queues, real-time reasoning, watchdog/health monitoring, network protocol, fault injection and test traceability transfer. Linux kernel scheduling/driver model, device tree, Yocto, systemd/init, tracing and PREEMPT_RT specifics do not transfer automatically.
VX2. Làm sao thiết kế telemetry packet parser chống lỗi?
Validate datagram/framing and min/max length before indexing; guard arithmetic overflow, version/APID/ID allowlist, sequence/freshness and integrity checks. Bound allocation/work/log rate; fuzz truncated/oversized/random payload. Keep control path nonblocking.
VX3. Nếu FreeRTOS+TCP buffers cạn vì telemetry burst?
Track buffer/drop counters, bound receive/send queue and work, shed/coalesce low-priority telemetry, preserve fault/control messages. Test sustained overload; increasing buffers only treats burst not producer-consumer rate mismatch.
VX4. Cross-node latency đo sao khi clocks chưa sync?
Use round-trip timestamp from one clock, or establish sync protocol plus offset/error bound. Don't subtract unsynchronized timestamps for one-way latency. Report host/virtual-time distinction for QEMU.
VX5. CCSDS telemetry packet có thể đặt thẳng trong UDP không?
Application can transport CCSDS Space Packets via UDP datagrams if system interface defines it, but packet layer is not the physical/link layer. Define encapsulation, packet length, APID/sequence/time fields and parser bounds; optional project module is not implemented unless evidence shows it.
VX6. So QNX, FreeRTOS, Linux scheduler thế nào?
Compare execution model, isolation and real-time configuration, not numeric priority values. QNX uses process/thread and native IPC; FreeRTOS tasks share address space by default with MPU option; Linux task/kernel/driver behavior depends kernel/config. Benchmark same deadline/workload and inspect blocking/interrupt paths.

Lab A · Task priority experiment

  1. Create low task that owns a mutex and does short bounded work; high task waits on it; medium task produces CPU load.
  2. Run without PI then with mutex PI where applicable; timestamp high task block duration.
  3. Repeat without holding lock around artificial delay; compare root-cause design with priority adjustment.
  4. Record exact config, task priorities, timing clock and limitations of QEMU.

Lab B · ISR event to task

Use a modeled interrupt or timer callback in the selected demo. ISR captures a counter and sends notification through correct FromISR API; task does processing. Run step targets at several amplitudes, saturation/anti-windup cases, noisy/stuck encoder. Export p50/p99/max response/jitter with sample count; generate missed-deadline and queue-age report. Separate plant behavior from scheduler timing.

TermÝ nghĩa
TCBTask Control Block: kernel metadata/state của task.

ISRInterrupt Service Routine; bounded interrupt-context handler.
FromISRFreeRTOS API variant dành cho ISR context.

WCETWorst-case execution-time bound under explicit assumptions.
