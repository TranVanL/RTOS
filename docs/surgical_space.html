1 · Nền tảng chung mà interviewer kỳ vọng

Correctness

Input validation, state invariants, ownership, integer bounds, error paths, reentrancy, lifetime.

Timing & resources

Latency budget, memory/stack/CPU/network budget, overload policy, watchdog and bounded work.

Maintainability

Interfaces, layering, versioning, reviewability, traceable requirements, reproducible builds.

Evidence

Tests, logs, traces, target/build identity, reproducible reproduction, observed limitations.

Design review checklist

  • What is the single source of truth for state? Which component owns each mutable field?
  • Can a function block, allocate, wait on a lock, or call callbacks? Is that allowed in its context?
  • What happens on malformed input, partial I/O, timeout, cancellation, restart, duplicate command and resource exhaustion?
  • Are units, endian, scaling, signedness, bounds and version encoded in the interface?
  • Can logging, tracing or telemetry perturb the critical path? What is the bounded queue/drop policy?
  • Which claims are tested on host, QEMU, target hardware, HIL or qualified environment?

Behavioral interview story bank

Chuẩn bị 5 câu chuyện STAR (Situation–Task–Action–Result): timing/concurrency bug; integration problem; failure/debug; design trade-off; quality/safety disagreement. Mỗi câu chuyện nên có symptom đo được, vai trò cá nhân, quyết định, evidence trước/sau và bài học. Không bịa số hoặc nhận công lao của team.

2 · C/C++ và embedded coding: câu hỏi senior hay đào

C memory model & ownership

  • volatile phù hợp cho memory-mapped I/O hoặc một số compiler-visible side effects; nó không làm thao tác atomic, không tự đồng bộ thread/ISR và không tạo memory barrier phổ quát.
  • Concurrent access cần atomic primitive/critical section/lock phù hợp; dữ liệu nhiều field cần invariant snapshot chứ không chỉ bảo vệ từng biến rời.
  • Pointer lifetime: stack/local buffer không được gửi sang consumer bất đồng bộ sau khi function return; define ownership transfer/reuse explicitly.
  • Integer overflow, signed/unsigned conversion, shift width, alignment, strict aliasing, uninitialized data và use-after-free là lỗi embedded thực tế.
  • MMIO access phải theo datasheet/compiler/architecture rules; register width, ordering, read-to-clear/write-one-to-clear semantics có thể quan trọng.

Coding standards và review

Với C/C++ embedded, interviewer có thể hỏi MISRA C/C++ hoặc project coding standard. Trả lời không chỉ “theo MISRA”: coding rules giảm ambiguity/risk nhưng cần deviation process, static-analysis configuration, code review và rationale. Phân biệt language standard, compiler extension, vendor HAL, generated code và third-party software.

Hỏi: Vì sao không dùng volatile cho biến dùng chung giữa ISR và task?
Volatile buộc compiler thực hiện observable accesses theo implementation, nhưng không bảo đảm atomic read-modify-write, ordering giữa nhiều field hay mutual exclusion. Dùng atomic nếu lock-free semantics/ISR support được xác nhận; nếu không, critical section đủ ngắn hoặc ISR-to-task queue/notification với data ownership rõ.
Hỏi: Có nên dùng dynamic memory trong real-time path?
Không có câu trả lời tuyệt đối. Runtime allocation có thể có latency/fragmentation/failure variance. Với deadline-critical path thường preallocate/fixed pool hoặc static allocation; nếu allocate động, bound allocator behavior, lifetime, fragmentation, exhaustion response và đo target. Nêu policy, không chỉ khẩu hiệu.
Hỏi: Làm sao thiết kế C API ổn định giữa QNX và MCU firmware?
Định nghĩa fixed-width types, endian, units, version/length, error codes, alignment and ownership. Không serialize native struct trực tiếp nếu padding/ABI khác; dùng pack/unpack explicit functions và shared test vectors (C ↔ Python), bounds tests and fuzzing.

3 · Linux user-space, process, concurrency và diagnostics

System programming map

Application / service → libc + POSIX (pthread, clock, file descriptors, sockets) → syscalls → Linux kernel (scheduler, VM, VFS, networking, drivers) → device tree / firmware description + SoC peripherals

QNX/POSIX/FreeRTOS concepts transfer partially; Linux scheduling policy, kernel driver model, device tree, init, filesystem, cgroups and diagnostics are platform-specific. Luôn nói “theo Linux target/kernel config này”, không suy từ RTOS behavior.

Concurrency primitives / traps

  • pthread_mutex bảo vệ shared state; condition variable luôn dùng vòng lặp predicate vì spurious wakeups/race giữa unlock và wait.
  • Signals là asynchronous process/thread notifications; signal handler bị giới hạn async-signal-safe operations.
  • epoll/poll phù hợp multiplex file descriptors; nonblocking sockets cần xử lý partial reads/writes, EAGAIN and framing.
  • Process isolation khác threads sharing address space; shared memory đòi hỏi synchronization, lifetime and permission design.
  • FD leaks, zombie processes, inherited descriptors, fork/exec interactions and shutdown ordering là operational bugs.
  • Thread priority alone doesn't guarantee deadline: page faults, blocking I/O, scheduler policy, RT throttling, IRQ affinity and kernel critical sections matter.

Linux real-time & performance reasoning

For latency-sensitive Linux, evaluate PREEMPT_RT status/config, thread policy, IRQ threading/affinity, memory locking, page faults, CPU frequency/power states and driver paths on the actual target. PREEMPT_RT improves preemptibility but does not automatically prove WCET or remove all non-preemptible sections.

Hỏi: Epoll server bị packet split hoặc ghép thì sao?
TCP is a byte stream, not a message protocol. Implement framing (length/magic/version), incremental parser state, max-size checks, partial read/write handling, timeouts/backpressure and fuzz tests. UDP preserves datagram boundaries but may lose/reorder/duplicate datagrams; validate each independently.
Hỏi: Điều tra latency tăng sau release như thế nào?
Compare exact build/config and workload; split app queueing, syscall/network, scheduler/IRQ and device response. Capture low-overhead trace, perf counters/logs, CPU/memory pressure and percentile distributions. Reproduce, change one variable, then add a regression test. Avoid starting with priority changes.

4 · Build/release engineering, cybersecurity và platform lifecycle

Reproducible product builds

  • Pin source revisions, toolchain/sysroot, build flags, environment, generated sources and dependency manifests.
  • Track configuration separately by board/product/variant; review differences and prevent accidental debug settings in release.
  • Record build ID, compiler, kernel, root filesystem and firmware versions in artifacts/logs; archive symbols for crash analysis.
  • For Yocto, understand layers/recipes, machine/distro configuration, SDK/sysroot, sstate cache, image manifest and license/SBOM obligations. Build reproducibility is more than “bitbake succeeded”.
  • Deployment: versioned update, integrity/authenticity, power-loss behavior, rollback/recovery and compatibility between app/firmware/protocol.

Secure design baseline

Threat model

Assets, actors, entry points, trust boundaries, misuse cases and security assumptions.

Identity & access

Least privilege, authenticated management, key storage, service permissions, no debug backdoor.

Update lifecycle

Signed package, secure boot chain where required, anti-rollback policy, recovery and key rotation.

Vulnerability response

SBOM, dependency/version tracking, triage, patch verification, disclosure and support period.

Safety and security intersect but are not the same. A fail-safe design can still be vulnerable to malicious command injection; encryption does not prove a system safe under random faults. Derive controls from product threat/risk model.

Operational observability

  • Structured event code + timestamp source + monotonic sequence + component/build version.
  • Bounded logging with severity, rate limiting, rotation/persistence policy and drop counter.
  • Health endpoint reports semantic readiness, not just process alive: self-test, peer freshness, resource pressure, degraded/fault state.
  • Crash dump/fault record must be correlated to exact binary, symbols and config; protect privacy/security-sensitive data.

Coverage is not correctness by itself

Line/branch/condition/MC/DC metrics have different scope and cost; required objective depends standards/product/software classification and process. Coverage percentage alone doesn't show requirement completeness, assertion quality, data validity or fault handling. Trace requirement → design/risk control → implementation → test result and review gaps.

Bug triage template

  1. Preserve failing binary/config, logs, core/fault record, target and steps to reproduce.
  2. Separate symptom, trigger, root cause, contributing conditions and impact.
  3. Assess affected requirements/risk controls/product versions; decide containment.
  4. Implement fix with review/static/unit/integration regression; test adjacent paths and negative cases.
  5. Update traceability, release note, anomaly/problem report and field action if needed.
SIL → HIL: simulation validates logic within a model; HIL/target tests validate real interfaces and timing assumptions. A QEMU test pass cannot substitute driver, electrical, power-loss, watchdog silicon, EMC, clinical or environmental qualification evidence.

6 · VinSurgical: medical-device software lifecycle

Basic software interview thường muốn biết bạn có thể làm code low-level trong môi trường có controlled process: requirements, architecture, implementation, verification, configuration, change control, anomaly handling and risk linkage. Hãy hỏi team về intended use, product lifecycle, applicable markets/standards and safety responsibilities instead of assuming.

Lifecycle artifacts interviewer may ask about

  • Software development plan, requirements, architecture/design, implementation, unit/integration/system verification and release.
  • Software safety classification and rationale under applicable process.
  • Risk analysis and traceable risk controls; verification that controls are implemented/effective.
  • Configuration management: source, tools, generated code, third-party/SOUP components, build/release identity.
  • Problem resolution/anomaly process, change-impact analysis, regression and maintenance.
  • Review records, test procedures/results, unresolved anomalies and release acceptance rationale.

Verification vs validation

Verification: “Did we build the software/system according to specified requirements?” → reviews, analysis, unit/integration/system tests against requirements Validation: “Does the product meet user needs and intended use in the intended environment?” → system/use scenarios, representative workflows, clinical/human-factors context

Both matter. A passing unit test verifies a narrow requirement; it does not validate intended use. Exact terminology and required process are controlled by the applicable quality/regulatory framework.

7 · Risk, safety and cybersecurity engineering

Risk reasoning chain

Hazard → foreseeable sequence of events → hazardous situation → harm ↓ Risk estimation (severity + probability model as applicable) ↓ Risk evaluation against criteria → risk control options ↓ Implement control → verify implementation/effectiveness ↓ Residual risk / benefit-risk / production and post-production monitoring

Do not reduce medical risk to “FMEA spreadsheet filled”. Risk management is lifecycle and system-level; software may contribute to a hazard or implement a control. Analyze control independence, common cause, detection latency, usability, foreseeable misuse and failure response.

Control hierarchy and fault containment

  • Design inherently safer where feasible; add protective measures; then information/training as appropriate to the process.
  • Define safe behavior for loss of sensor, stale command, processor reset, communications loss, corrupted state and brownout.
  • A software “disable” flag is not necessarily a physical safe state; understand power stage, brake/load, independent interlock and feedback.
  • Fault detection must be timely and sufficiently independent from the failure it detects; watchdog kick source matters.
  • Degraded mode must have explicit permitted functions, limits, timeout and exit/reset conditions.

Cybersecurity meets safety

  • Threat model privileged update, debug interfaces, network commands, service ports, credentials and third-party libraries.
  • Authenticate/authorize state-changing commands; CRC only detects certain accidental errors, not malicious tampering.
  • Secure update/recovery and vulnerability response need field lifecycle; patch cannot silently invalidate risk controls.
  • Consider availability attacks: packet flood/queue exhaustion/log storms can become safety-relevant availability failures.
  • Include security requirements, architecture, verification and post-market monitoring according to applicable guidance.
Scenario: control software detects excessive force, but sensor can fail low
Do not jump straight to threshold code. Clarify hazard and system safety requirement; analyze sensor failure modes/diagnostics and independence; define response latency and actuator safe behavior; use redundant/plausibility checks only if justified; trace risk control to implementation/test; inject stuck-low, disconnected, noisy and stale sensor faults; validate physical behavior with representative hardware. A SIL test demonstrates logic only.

8 · VinSurgical: Basic Software architecture & implementation

What “basic software” can include

Scope varies by organization, but may cover OS adaptation, startup, drivers/HAL, communication services, diagnostics, watchdog/health monitoring, resource management, boot/update and common libraries. Clarify ownership boundary: BSP/vendor, platform team, product application, safety system, cybersecurity and regulatory quality.

Interface contract for a safety-relevant service

  • Explicit states and legal transitions; distinguish command accepted, command executed and physical outcome confirmed.
  • Input schema: units/range/enum/version/length; stale sequence/session commands rejected.
  • Output semantics: status validity, freshness, fault cause, timeout, retry and recovery.
  • Concurrency: single writer, lock/blocking model, priority/ISR context, bounded response.
  • Configuration: checksum/version, safe defaults, invalid configuration response and change traceability.
  • Diagnostic event: immutable cause code, timestamp source, context and log overflow policy.

SOUP / third-party software mental checklist

Identify exact component/version/source and intended use; evaluate supplier evidence and known anomalies; assess safety/security impact and interfaces; pin build inputs; define update monitoring and change-impact review; test integration and failure behavior. “Open source” neither means automatically acceptable nor automatically unsafe.

Good code review comments

  • Which requirement/risk control does this change implement?
  • Are units and bounds explicit? Could signed arithmetic overflow?
  • Can this path block, allocate, log, or wait on a lock at high priority/ISR context?
  • What happens on reset halfway through state update or flash/config write?
  • Can an old, duplicated or unauthorized command cause repeated action?
  • Which test proves the failure case and which hardware assumption is still open?

9 · VinSurgical: câu hỏi interview chuyên sâu

VS1. IEC 62304 có chứng nhận sản phẩm medical device không?
Không nên diễn đạt như chứng nhận độc lập của sản phẩm. Đây là software lifecycle process standard/framework trong medical-device context. Product conformity involves applicable standards/regulatory route, QMS, risk management, system verification/validation and evidence; confirm scope with regulatory/quality team.
VS2. Safety class phần mềm xác định thế nào?
The applicable process classifies software based on potential contribution to hazardous situations/harm and risk-control architecture. Explain that classification is justified through the project risk process and standard edition; do not assign a class from code size or role title alone.
VS3. Verification khác validation?
Verification checks outputs against specified requirements/design; validation checks whether system meets intended use/user needs in representative context. Give one unit test versus one end-to-end/user workflow example.
VS4. Risk control nào quan trọng hơn: software alarm hay hardware interlock?
Depends on hazard analysis and architecture. Prefer controls that reduce risk effectively and independently where needed; software alarm may not prevent harm if operator cannot react in time. State assumptions, failure independence and verification evidence—do not prescribe without system context.
VS5. Làm sao chứng minh a watchdog works?
Specify faults it detects, timeout and reaction; show kick depends on critical task health; inject stall/priority starvation; measure detection-to-output/reset; test false positives, restart/re-enable gate and retained diagnostics. Watchdog alone doesn't guarantee physical safe state.
VS6. Khi nào bug thành safety issue?
Assess affected requirements/functions and hazard/risk controls, use-error and system context; enter formal anomaly/change process, contain affected release, link analysis and regression. Severity is not determined solely by crash frequency.
VS7. How do you handle SOUP/library CVE?
Identify affected versions/configuration and exploitability/exposure, evaluate safety/security impact, compensating controls and update route, create traceable decision, test candidate update/regressions and monitor lifecycle. Follow organization's vulnerability process and applicable regulator guidance.
VS8. Coverage 100% có nghĩa software safe không?
No. Coverage is a measure of exercised code/conditions under a defined method; it doesn't prove requirements completeness, test oracle quality, risk control effectiveness or absence of systematic defects. Use appropriate coverage objective alongside reviews, analysis, traceability and system tests.
VS9. Change nhỏ trong driver có cần regression không?
Use impact analysis across driver interface, timing, error paths, affected configurations, dependent services and hazards. Test scope is risk-based and documented; small diff isn't necessarily small system impact.
VS10. Project SIL có thể claim medical safety compliant?
No. It demonstrates selected engineering mechanisms and testability; it lacks actual intended-use device, clinical/system context, full QMS/risk lifecycle, target hardware evidence and conformity assessment. State precisely what was built/run and what remains.
VS11. Safe state luôn là actuator OFF?
No. A held/gravity-loaded instrument may need controlled brake/hold; immediate disable could introduce risk. Safe state is system/hazard-specific, specified with system engineers and verified on real actuator/load.
VS12. How would you prevent a bad configuration from enabling motion?
Schema/version/range validation, integrity/authenticity as appropriate, safe defaults, startup self-test, configuration compatibility and explicit arm/enable sequence; invalid config prevents operation and records cause. Test power-loss/partial update and downgrade/replay cases.

10 · VinSpace: Linux platform knowledge beyond booting a kernel

Boot-to-service chain

ROM / boot firmware → bootloader → kernel + DTB + initramfs/rootfs → early console / driver probe / mount root filesystem → PID 1 (init/system manager) → target services → application health/readiness → operational mode

For every stage ask: who supplies it, how configured, how logs are captured, what happens when dependency fails, how rollback/recovery works, and how exact image is identified.

Yocto / cross-build review at senior level

  • Explain layer, recipe, append, machine/distro config, image recipe and dependency graph without calling Yocto “just a build script”.
  • Use target SDK/sysroot and correct triplet/ABI; avoid host headers/libraries contaminating cross-build.
  • Understand package/image manifests, kernel/module versions, rootfs composition, licensing and SBOM.
  • Reproduce from pinned layers/revisions/config; document sstate use, build provenance and release artifact hashes.
  • Security update path: package ownership, CVE triage, backport validation, rootfs strategy and recovery.

Driver / Device Tree questions (advanced refresher)

  • Probe path: compatible match → resources (reg/IRQ/clock/reset/regulator/DMA) → initialization → registration/consumer binding.
  • Probe defer is not necessarily failure; dependency may become available later. Diagnose deferred-probe loops and error codes.
  • Interrupt top/bottom-half/threaded handling; never assume hard IRQ can sleep.
  • DMA addresses, cache coherency, mapping API and buffer lifetime are distinct from CPU virtual/physical addresses.
  • Device Tree describes hardware, not driver algorithm; binding/schema and exact compatible semantics matter.
  • Power management, suspend/resume, runtime PM and shared clocks/reset need lifecycle testing.

Systemd/service lifecycle and recovery

Define dependencies and readiness (not only process started), restart/backoff policy, watchdog integration, privilege/capability, resource limits, logs, shutdown ordering and update rollback. Restart loops can worsen overload; readiness should expose degraded state rather than hide failed hardware.

Target diagnostics

Examples when included in image: kernel boot log, system journal, sysfs/procfs, tracefs/ftrace, perf, strace, gdb/core, network counters and platform-specific health telemetry. Tool availability/overhead varies. Build an observation plan before failure occurs: persistent ring logs, crash dump storage, monotonic timestamps and version/symbol mapping.

11 · VinSpace: space-system dependability & FDIR

Space systems often face constrained power/compute/communication, long unattended operation, delayed ground contact and limited repair. Exact mission requirements vary: treat radiation tolerance, redundancy, autonomy, lifetime and ECSS/CCSDS applicability as system-defined, not assumed from the word “space”.

FDIR: Fault Detection, Isolation and Recovery

  • Detect: heartbeat/progress, range/plausibility, timeout, ECC/bus/driver status, cross-monitor residual.
  • Isolate: identify failed unit/channel/task; avoid common-cause assumptions; prevent fault propagation.
  • Recover: retry boundedly, reset subsystem, switch redundant lane, enter safe mode or request ground intervention.
  • Report: preserve cause/time/context and distinguish original fault from recovery action.
  • Define inhibit/enable conditions and prevent reset storms or repeated hazardous command execution.

Radiation and hardware faults: what software engineer should know

Potential effects include transient bit upset, latch-up, functional interrupt and accumulated degradation, depending technology/mission environment. Software mitigations may include ECC/status monitoring, memory scrubbing where supported, watchdogs, checkpoint/restart, redundancy/voting, range/plausibility checks and safe mode. They require hardware/system fault model and independence analysis; software cannot promise immunity to radiation.

Redundancy is not just duplicate boards

  • Cold/warm/hot redundancy trades power, switchover time and common-mode exposure.
  • Redundant channels need independent power/clock/sensor/communication paths where required.
  • Voting needs defined behavior for disagreement, timeout and voter failure.
  • Failover can propagate stale state; define epoch, state transfer, command fencing and authority ownership.
  • Independent watchdog/safety path must not share the exact failure that it is intended to catch.

Safe mode and command authority

Define which functions remain available, minimum telemetry, power/thermal constraints, command authentication/authorization, local autonomy and recovery conditions. “Safe mode” is a controlled operational mode—not simply reboot or turn everything off.

Hỏi: Radiation upset hay software bug?
Preserve telemetry/registers, event timeline, ECC/exception/processor reset cause and build/config; compare occurrence correlation with environment, memory location and reproducibility. Avoid premature attribution. Design diagnostics to distinguish transient hardware fault, systematic defect, power/clock event and interface corruption.

12 · CCSDS, telemetry/telecommand, time and data integrity

Layering: packet is not the whole link

CCSDS Space Packet is a packet-layer concept. A real link may also define transfer frames, channel coding, synchronization, physical layer, retransmission/virtual channels and mission-specific services. A UDP datagram carrying a CCSDS-like packet is an application transport choice, not a complete spacecraft link implementation.

Space Packet Primary Header mental model

Common Space Packet primary header is 6 octets and includes version, packet type, secondary-header flag, APID, sequence flags/count and packet data length. Packet data length field conventionally represents data-field octets minus one. Confirm current CCSDS edition/profile and byte encoding before parser implementation.

Robust telemetry/telecommand design

  • Validate minimum header, packet length, maximum configured size and arithmetic overflow before accessing payload.
  • APID/message allowlist, sequence/segmentation semantics, version and secondary-header interpretation explicit.
  • Time tag includes epoch, unit, rollover, validity/synchronization quality and clock reset behavior.
  • Distinguish command acceptance, execution completion and resulting state telemetry.
  • Telecommand freshness, replay prevention, authentication/authorization and idempotency are security/system decisions; CRC is not authentication.
  • Telemetry backlog policy: prioritize critical fault/health, coalesce periodic snapshots, bound memory and count drops.
  • Parser fuzzing: truncated, oversized, malformed length, unknown APID, bad sequence, duplicate/replay and random bytes.

Time synchronization

Separate monotonic elapsed time (timeouts/latency) from mission/UTC time (event correlation). If nodes have unsynchronized clocks, do not claim one-way latency from their timestamps. Track time-source quality, offset/uncertainty, reset, rollover and leap/time-scale conventions as applicable.

Project supplement: CCSDS telemetry is an optional module in the project plan. Unless decoder/encoder, test vectors and packet captures exist, describe it as planned/design exercise—not completed implementation.

13 · VinSpace: câu hỏi interview chuyên sâu

VX1. Explain Linux boot failure where kernel starts but service is absent.
Trace bootloader args/DTB, kernel probe and rootfs mount, PID 1/service dependencies, missing libraries/config/permissions, readiness and restart logs. Capture persistent logs and exact image hashes; distinguish kernel panic, failed mount, failed probe and app exit.
VX2. What is the value of Device Tree?
It describes discoverable hardware/resources to the kernel and drivers; compatible/bindings plus properties define interface. It is not a place for driver algorithm or arbitrary policy. Validate schema/addresses/interrupts/clocks and match target revision.
VX3. A driver probes but device I/O times out—next steps?
Check resource mapping/clock/reset/power/IRQ/DMA configuration, bus transactions and error status, runtime PM, pinmux and hardware revision. Inspect kernel trace/log and datasheet; instrument the smallest path. Probe success doesn't prove functional communication.
VX4. PREEMPT_RT enabled—can you promise deadlines?
No. It changes kernel preemptibility/IRQ handling but deadlines depend hardware, drivers, scheduler, priority, locks, non-preemptible paths and load. Define workload, measure worst observed and analyze bounds on target; account for RT throttling and priority inversion.
VX5. How do you avoid priority inversion on Linux?
Short lock hold times, appropriate PI mutex where supported, lock ordering, avoid blocking I/O under locks, priority-aware IPC and tracing lock contention. Analyze IRQ/thread priorities and resource dependencies; don't just raise SCHED_FIFO priority.
VX6. What breaks reproducibility in Yocto?
Unpinned layers/source, floating dependencies, host contamination, undocumented distro/machine config, generated timestamps/environment, network fetch variability and untracked patches. Pin inputs, mirror sources, record build metadata and compare artifacts/manifests.
VX7. Packet parser gets length 0xFFFF—what now?
Reject based on max protocol/frame size before allocation/indexing; guard integer arithmetic and framing; count error without log flood; preserve parser synchronization; fuzz and regression-test. Never trust packet-declared size.
VX8. How do you debug an intermittent target-only crash?
Keep exact symbols/build IDs, persistent crash/core or register dump, boot logs, resource metrics, monotonic event sequence and reproduction conditions. Compare compiler/config/memory layout; use sanitizers on host analogue, target trace and stress/fault injection.
VX9. What is FDIR?
Fault Detection, Isolation and Recovery: detect abnormal behavior, identify/contain the affected component, then recover to a defined operational/safe mode and report. Include false positives, common cause, bounded retries and command/state reconciliation.
VX10. Explain CCSDS Space Packet vs UDP.
Space Packet is packet framing/metadata at an application protocol layer; UDP is a transport protocol. UDP datagram can carry a packet in a chosen interface but does not itself implement transfer frames, link coding, mission services or command authentication.
VX11. Why can watchdog reset be dangerous?
Reset may create a loop, lose volatile fault context, leave hardware outputs in undefined state or replay stale commands. Define independent output behavior, reset cause logging, backoff/latching, startup self-test and explicit re-arm/ground recovery.
VX12. How do you treat single-event upset in software?
Use hardware-provided ECC/telemetry and system fault model; detect/correct where supported, scrub/checkpoint/restart/redundancy as allocated; test injected corruption and recovery. Do not claim software alone provides radiation hardness.
VX13. RT scheduling Linux vs QNX vs FreeRTOS?
Compare semantics and configuration, not numeric priorities. Linux can use RT policies/IRQ-thread tuning; QNX has its scheduler and IPC; FreeRTOS has fixed-priority task scheduler. In every case analyze blocking, interrupts, resource contention, and measure on target.
VX14. How do you design a software update for an unattended embedded target?
Authenticated package and version compatibility, atomic/dual-partition or recoverable update, power-loss tests, rollback/anti-rollback policy, configuration/data migration and health-confirmed activation. Security keys, recovery authority and support lifecycle matter.

14 · System-design cases để whiteboard

Case A — Medical motion platform reports a stuck position sensor

  1. Ask requirement and hazard context: allowable error, motion/load, detection budget, defined safe state.
  2. Draw sensor → acquisition/driver → validation → control → actuator and diagnostic paths.
  3. Define stale/range/plausibility detection, degraded behavior, latch/reset authorization and independent hardware path if required.
  4. Specify traceable tests: stuck, drift, noise, disconnect, delayed sample, concurrent command, restart.
  5. State what needs hardware/HIL/clinical context; do not claim SIL proves physical safety.

Case B — Linux telemetry service loses packets only under burst

  1. Confirm transport, MTU, packet rate, receive buffer, socket mode, CPU/IRQ and consumer rate.
  2. Measure NIC/kernel drops, socket queue, app queue, parser time, scheduling latency and log overhead.
  3. Bound queue and set priority/coalescing policy; distinguish critical fault from periodic telemetry.
  4. Stress burst and sustained overload; report drop point, recovery and resource high-water.
  5. Validate on target driver/network rather than only localhost simulation.

Case C — Redundant controller failover may replay an old command

  1. Define authoritative leader/epoch and how a peer proves current authority.
  2. Fence old sender; reject stale sequence/session and commands created before failover.
  3. Transfer/reconcile state before enabling output; handle split-brain and uncertain commit result.
  4. Test failover during command, ack loss, reboot, time drift and network partition.

Case D — Release passes tests but fails at boot on one board revision

Compare image/DTB/BSP/hardware revision; preserve boot log and probe order; check resource mapping, pinmux, power/clock and feature flags; identify what changed; create revision-specific automated test and release gating. Don’t patch by adding delay before understanding dependency.
